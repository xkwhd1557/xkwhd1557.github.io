3 재현 가능한 작업 환경

3장 재현 가능한 작업 환경(Reproducible Workflow)

데이터 사이언스·AI
데이터 사이언스 개론
데이터 분석의 결과를 다른 사람과 미래의 내가 그대로 다시 얻을 수 있도록 하는 재현 가능성이 왜 중요한지 살펴보고, 셸과 배쉬, 좋은 코드와 코드 스타일, 깃을 이용한 버전 관리, 가상 환경과 컨테이너, 단위 테스트로 이어지는 3장의 흐름을 정리합니다.
Published

November 4, 2026

들어가며

2장에서는 데이터를 숫자와 그림으로 요약하는 방법을 파이썬으로 살펴보았습니다. 그런데 실제 데이터 분석은 깔끔하게 정리된 작은 데이터를 파이썬으로 불러오는 데서 시작하지 않는 경우가 많습니다. 데이터가 너무 커서 파이썬으로 바로 열리지 않을 수도 있고, 분석 코드를 몇 달 동안 고치다 보면 어느 버전의 코드로 어떤 결과를 냈는지 헷갈리기 시작하며, 내 컴퓨터에서는 잘 돌던 코드가 다른 사람의 컴퓨터에서는 오류를 내기도 합니다.

3장에서는 이런 문제들을 다루는 도구들을 살펴봅니다. 언뜻 보면 서로 별 관계가 없어 보이는 도구들이지만, 모두 하나의 목표를 향하고 있습니다. 바로 재현 가능성(reproducibility)입니다.

재현 가능성이란 무엇일까요?

재현 가능성은 같은 데이터와 같은 코드로 같은 결과를 다시 얻을 수 있는가를 뜻합니다. 다른 사람이 내 분석을 따라 했을 때 나와 같은 결론에 이를 수 있어야 하고, 몇 달 뒤의 내가 예전 분석을 다시 돌렸을 때도 같은 숫자가 나와야 합니다.

당연한 이야기처럼 들리지만, 실제로는 이것이 생각보다 자주 깨집니다. 과학 연구에서는 2010년대에 이 문제가 크게 불거졌습니다. 예를 들어 2015년에는 270여 명의 연구자가 저명한 심리학 학술지에 실린 연구 100편을 같은 방법으로 다시 실험해 보았는데, 원래 연구에서는 97퍼센트가 통계적으로 의미 있는 결과를 보고했지만, 다시 해 본 실험에서는 그 비율이 36퍼센트에 그쳤습니다.1 이렇게 발표된 연구 결과가 다시 해 보면 재현되지 않는 현상을 흔히 재현성 위기(replication crisis)라고 부릅니다.

그 원인으로 자주 꼽히는 것 가운데 하나가 p-해킹(p-hacking)입니다. 통계에서는 데이터가 어떤 주장을 얼마나 뒷받침하는지를 판단할 때 p-값(p-value)이라는 수치를 흔히 씁니다. 이 값이 미리 정해 둔 기준보다 작으면 “통계적으로 의미 있는” 결과라고 판단하는데, 분석하는 사람이 원하는 결과가 나올 때까지 데이터를 이리저리 나누거나, 일부를 빼거나, 분석 방법을 바꿔 가며 계산을 반복하면 우연히 기준을 통과하는 결과를 얻을 수 있습니다. 이렇게 얻은 결과는 우연의 산물일 가능성이 높기 때문에, 다른 사람이 다시 해 보면 재현되지 않습니다. p-값이 무엇이고 왜 이런 일이 생기는지는 4장에서 자세히 다룹니다.

이런 일을 겪으면서, 이제는 새로운 연구가 나오면 그 결과가 얼마나 놀라운지만큼이나 그 과정을 다른 사람이 그대로 따라 할 수 있는지를 중요하게 봅니다. 재현할 수 없는 결과는 아무리 대단해 보여도 “운이 좋았던 것은 아닐까?”, “누군가 데이터에 손을 댄 것은 아닐까?”라는 의심을 피하기 어렵습니다. 재현 가능성이 곧 신뢰성의 지표가 된 것입니다.

데이터 사이언스도 마찬가지입니다. 1.3에서 보았듯이 데이터 분석은 질문을 세우고, 데이터를 탐색하고, 모델을 만들고, 결과를 해석하는 과정을 여러 번 오가며 진행됩니다. 이 과정에서 무엇을 어떤 순서로 했는지 기록이 남지 않으면, 결과를 다른 사람에게 설명할 수도, 스스로 검증할 수도 없습니다. 그리고 재현 가능성은 이해 가능성과도 맞닿아 있습니다. 코드를 이해하지 못하면 재현할 수 없고, 재현할 수 없는 결과는 이해할 가치가 별로 없으니까요.

무엇이 재현을 가로막을까요?

같은 분석을 다시 해도 같은 결과가 나오지 않는 이유는 크게 네 가지로 나눠 볼 수 있습니다. 3장의 각 부분은 이 가운데 하나씩을 다룹니다.

  • 과정이 기록되지 않는다. 데이터를 엑셀에서 마우스로 고치거나 필터를 걸고 지우면, 무엇을 어떻게 했는지 남지 않습니다. 반면 명령어와 스크립트로 처리하면 그 명령어 자체가 기록이 됩니다. 3.1부터 3.4까지는 큰 데이터를 가볍게 훑고 걸러 내는 도구인 셸과 배쉬를 다룹니다.
  • 코드를 읽을 수 없다. 기록이 남아 있어도 그 코드를 다른 사람이, 혹은 미래의 내가 읽고 이해할 수 없다면 소용이 없습니다. AI가 코드를 대신 써 주는 요즘에는 더욱 그렇습니다. 3.5와 3.6에서는 좋은 코드란 무엇인지, 그리고 파이썬에서 읽기 좋은 코드를 쓰기 위한 코드 스타일을 다룹니다.
  • 코드와 데이터가 계속 바뀐다. 분석 코드는 계속 고쳐지고, 데이터도 새로 들어옵니다. 어느 시점의 코드와 데이터로 어떤 결과를 냈는지 기록해 두지 않으면 같은 결과를 다시 얻을 수 없습니다. 3.7과 3.8에서는 깃(Git)을 이용한 버전 관리를 다룹니다.
  • 실행 환경이 다르다. 같은 코드라도 운영체제나 라이브러리의 버전이 다르면 다르게 동작할 수 있습니다. 3.9에서는 가상 환경과 컨테이너로 실행 환경을 고정하는 법을, 3.10에서는 코드가 의도대로 동작하는지 자동으로 확인하는 단위 테스트를 다룹니다.

이 장의 흐름

  • 3.1 셸과 배쉬 시작하기: 큰 데이터를 다룰 때 셸이 왜 필요한지 살펴보고, 운영체제별로 배쉬를 설치합니다.
  • 3.2 배쉬 기본 명령어와 파이프: 배쉬의 기본 명령어와, 명령어들을 잇는 파이프와 리다이렉션을 익힙니다.
  • 3.3 배쉬 스크립팅: 변수, 조건문, 반복문, 스트림을 익히고, 명령어들을 스크립트 파일로 만들어 실행합니다.
  • 3.4 배쉬로 하는 탐색적 데이터 분석: 퀴즈쇼 데이터와 같은 형식의 연습 데이터로, 배쉬만 가지고 데이터를 훑고 골라내고 세어 봅니다.
  • 3.5 좋은 코드란 무엇일까요?: 가독성, 재현성, 일관성, 정확성, 재사용성, 견고함이라는 좋은 코드의 성질과, 코드를 사람이 읽는 글처럼 쓰자는 문학적 프로그래밍을 소개합니다.
  • 3.6 파이썬 코드 스타일과 AI 시대의 코드 검토: 파이썬의 철학과 PEP 8 스타일 가이드, 포매터와 린터, 그리고 AI가 짠 코드를 검토할 때 확인할 점을 다룹니다.
  • 3.7 깃으로 시작하는 버전 관리: 버전 관리와 깃의 원리를 이해하고, 저장소를 만들어 변경 사항을 기록해 봅니다.
  • 3.8 브랜치, 병합, 그리고 깃허브: 과거로 돌아가는 법, 브랜치를 만들어 실험하고 합치는 법, 원격 저장소와 깃허브로 협업하는 법, 그리고 데이터의 버전 관리를 다룹니다.
  • 3.9 가상 환경과 컨테이너: 파이썬 가상 환경과 도커 컨테이너로 실행 환경을 고정하고 공유하는 법을 다룹니다.
  • 3.10 단위 테스트: pytest로 함수가 의도대로 동작하는지 자동으로 확인하고, 테스트가 재현 가능성과 어떻게 이어지는지 살펴봅니다.

명령어가 꽤 많이 나오지만, 모두 외울 필요는 없습니다. 명령어는 필요할 때 검색하거나 AI에게 물어보면 됩니다. 중요한 것은 각 도구가 어떤 문제를 풀기 위해 있는지, 그리고 어떤 원리로 동작하는지를 이해하는 것입니다. 그래야 AI가 짜 준 명령어가 무슨 일을 하는지 판단할 수 있고, 문제가 생겼을 때 어디를 고쳐야 할지 알 수 있습니다.
