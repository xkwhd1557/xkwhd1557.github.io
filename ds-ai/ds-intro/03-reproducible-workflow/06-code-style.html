3.6 파이썬 코드 스타일과 AI 시대의 코드 검토

3장 재현 가능한 작업 환경 · PEP 8, 포매터와 린터, AI 코드 체크리스트

데이터 사이언스·AI
데이터 사이언스 개론
파이썬의 철학인 The Zen of Python과 스타일 가이드 PEP 8의 이름 짓기·줄 맞춤·주석 관례를 정리하고, 포매터와 린터로 스타일을 자동으로 점검하는 법, 그리고 AI가 짠 코드를 받아들이기 전에 확인할 점과 자주 나오는 오류를 예제로 살펴봅니다.
Published

November 4, 2026

들어가며

지난 글의 문학적 프로그래밍은 코드 한 줄 한 줄보다는 작업 전체를 읽기 좋게 만드는 철학이었습니다. 그래서 크누스의 WEB이나 주피터 노트북을 단순한 편집기라기보다 하나의 프로그래밍 시스템이라고 하는 편이 정확합니다. 이번 글에서는 한 단계 내려가서, 소스 코드 안에서의 가독성을 위한 코드 스타일(programming style)을 다룹니다.

좋은 코드 스타일의 기본은 이미 다들 알고 계실 것입니다. 코드는 이해하기 쉽게 써야 하고, 변수와 함수의 이름은 의미 있게 지어야 하며(수학 전공자들은 함수는 그냥 f, 변수는 x, y, z, a, b, c로 쓰는 경우가 많은데, 코드에서는 이런 습관을 버려야 합니다), 그 언어의 이름 짓기 관례를 따라야 한다는 것 등입니다. 이번 글에서는 파이썬의 코드 스타일을 조금 더 구체적으로 살펴보고, 마지막으로 AI가 짜 준 코드를 어떻게 검토할지 이야기하겠습니다.

The Zen of Python

모든 프로그래밍 언어에는 그 언어만의 철학이 묻어 있습니다. 프로그래밍 언어는 사람이 어떤 목적으로 기계를 다루기 위해 만든 발명품이라, 그 목적에 맞는 특성들이 있기 때문입니다. 파이썬의 철학은 파이썬에서 this라는 모듈을 불러오면 볼 수 있습니다.

import this
The Zen of Python, by Tim Peters

Beautiful is better than ugly.
Explicit is better than implicit.
Simple is better than complex.
Complex is better than complicated.
Flat is better than nested.
Sparse is better than dense.
Readability counts.
Special cases aren't special enough to break the rules.
Although practicality beats purity.
Errors should never pass silently.
Unless explicitly silenced.
In the face of ambiguity, refuse the temptation to guess.
There should be one-- and preferably only one --obvious way to do it.
Although that way may not be obvious at first unless you're Dutch.
Now is better than never.
Although never is often better than *right* now.
If the implementation is hard to explain, it's a bad idea.
If the implementation is easy to explain, it may be a good idea.
Namespaces are one honking great idea -- let's do more of those!

파이썬 초기 개발에 참여한 팀 피터스(Tim Peters)가 정리한 이 19줄은 흔히 The Zen of Python이라고 부릅니다. 쭉 훑어보면, 파이썬이 프로그래밍을 단순하고 명확하게 하자는 철학을 가지고 있다는 것이 보입니다. “아름다운 것이 추한 것보다 낫다”, “명시적인 것이 암시적인 것보다 낫다”, “단순한 것이 복잡한 것보다 낫다”, “가독성은 중요하다” 같은 문장들이지요. 단순함을 추구하는 이유는, 그래야 누구나 이해할 수 있는 코드가 만들어지기 때문입니다. 이것은 지난 글에서 이야기한 좋은 코드의 철학과 거의 그대로 겹칩니다. 파이썬이 데이터 사이언스에서 많이 쓰이는 이유를 여기서도 엿볼 수 있습니다.

PEP 8

PEP 8은 이런 파이썬의 철학을 코드에서 지키기 위한 스타일 가이드입니다.1 PEP는 Python Enhancement Proposal(파이썬 개선 제안서)의 줄임말로, 파이썬에 새로운 기능이나 관례를 제안하는 문서들에 번호를 붙인 것입니다. PEP 8은 그 8번 문서로, 한마디로 파이썬 코드 관례의 헌법 같은 문서입니다.

PEP 8을 지키지 않는다고 코드가 실행되지 않거나 오류가 나는 것은 아닙니다. 하지만 계속 이야기했듯이 이제 우리의 일은 코드를 쓰는 것보다 읽는 것에 가깝습니다. 그래서 PEP 8은 법처럼 익혀 두고 지키는 것이 좋습니다. 지키지 않으면 컴퓨터는 오류를 내지 않지만, 함께 일하는 동료들이 오류를 뿜어낼지도 모릅니다. 어기면 감옥에 가는 형법이라기보다는, 처벌은 없지만 웬만하면 지키자고 약속한 국제법 같은 것입니다. 아래에서는 PEP 8의 핵심과, PEP 8은 아니지만 함께 자주 이야기되는 조언들을 정리하겠습니다.

이름 짓기

파이썬에서는 모든 것이 객체이고, 객체를 만들거나 다룰 때 그것을 가리키는 이름, 즉 식별자(identifier)가 필요합니다. PEP 8은 무엇에 붙이는 이름인지에 따라 다음과 같은 모양을 쓰라고 합니다.

대상 모양 예시
클래스 단어의 첫 글자를 대문자로 이어 붙이는 CapWords (CamelCase라고도 합니다) BankAccount
함수, 메서드, 변수 소문자와 밑줄을 쓰는 snake_case add_balance(), customer_balance
상수 대문자와 밑줄 MAX_ITERATIONS = 1557
모듈 짧은 소문자 (필요하면 밑줄) numpy, pandas, seaborn

여기에 PEP 8 자체에 있는 규칙은 아니지만 널리 쓰이는 조언으로, 중복되는 맥락을 이름에서 빼라는 것이 있습니다. 예를 들어 Person이라는 클래스 안에서 그 사람의 나이를 나타내는 속성이라면, 이미 사람이라는 맥락이 있으니 person_age보다 그냥 age로 쓰는 편이 낫습니다. 쓸 때는 어차피 person.age처럼 쓰게 되니까요.

변수의 이름

변수의 이름은 기본적으로 명사로 짓고, 그 변수가 무엇을 담는지 잘 드러나게 지어야 합니다. 수학 전공자가 짠 코드에서 흔히 보이는 x, y, a, b 같은 맥락 없는 이름은 피합니다. 그래야 나중에 읽었을 때 그 변수가 무엇을 저장하는지 알 수 있습니다.

또 파이썬에서는 알아보기 어려운 줄임말보다 긴 이름이 낫다고 봅니다. C나 C++을 많이 쓰는 프로그래머들은 cre_tmstp처럼, 마치 한국어를 초성만으로 쓰듯 이름을 줄이는 경우가 많은데, 파이썬에서는 그럴 바에야 creation_timestamp처럼 풀어 쓰라고 권합니다.

그리고 단어를 일관되게 골라야 합니다. 고객의 이름을 client_name이라고 했다면, 고객의 나이도 client_age라고 해야지 갑자기 customer_age라고 하면 안 됩니다. 읽는 사람은 client와 customer가 서로 다른 무언가라고 생각할 수 있습니다.

매직 넘버(magic number)도 피해야 합니다. 프로그래밍에서 “매직”이라는 말이 붙으면 보통 치트키처럼 편리한 것을 떠올리기 쉬운데, 여기서는 좋게 말하면 신비로운, 나쁘게 말하면 정체를 알 수 없는 숫자라는 뜻입니다. 예를 들어 수치 해석에서는 근삿값이 참값에 충분히 가까워질 때까지 계산을 반복하는 경우가 많습니다. \(f(x) = 0\)의 해를 찾는 뉴턴 방법을 구현한 함수 newton_1d가 있고, 마지막 인자가 반복 횟수라고 해 보겠습니다.

newton_1d(f, df, x0, 1557)

이 코드를 처음 보는 사람은 “1557은 뭐지? 왜 하필 1557이지?”라는 의문을 품을 수밖에 없습니다.티~원 지금은 제가 반복 횟수라고 설명했으니 알 수 있지만, 더 복잡한 코드에서 설명 없이 이런 숫자를 만나면 그 의미를 알기 어렵습니다. 숫자에 이름을 붙여 두면 이 문제가 사라집니다.

MAX_ITERATIONS = 1557   # 뉴턴 방법의 최대 반복 횟수
newton_1d(f, df, x0, MAX_ITERATIONS)

리스트나 딕셔너리 같은 컨테이너를 담는 변수라면, 그 안에 무엇이 여러 개 들어 있는지 알 수 있게 짓는 것이 좋습니다. 보통은 names = ['김찬호', '박종우', '손인욱']처럼 복수형 명사를 쓰고, 자료형까지 드러내고 싶을 때는 names_list처럼 자료형을 이름에 붙이기도 합니다. 다만 이것은 PEP 8의 규칙이 아니라 사람마다 갈리는 취향에 가깝고, 요즘에는 이름에 자료형을 붙이는 대신 names: list[str] = [...]처럼 타입 힌트(type hint)로 자료형을 적는 방법도 많이 씁니다.

함수의 이름

함수도 변수와 비슷한 원칙을 따릅니다. 단어를 일관되게 고르고, 함수는 무언가를 하는 것이니 보통 load_data(), compute_mean()처럼 동사로 시작하는 이름을 붙입니다.

무엇보다 함수의 이름은 간단해야 합니다. 이름이 간단하지 않다는 것은 그 함수가 하는 일이 너무 많다는 신호일 수 있습니다. 그럴 때는 이름을 억지로 길게 짓기보다, 기능을 잘게 쪼개서 각각 간단한 함수로 만들고 그것들을 조합하는 편이 좋습니다. 함수 하나가 한 가지 일만 하면, 코드만 봐도 무엇을 하는지 알기 쉽습니다.

같은 이유로, True나 False를 받아서 함수가 하는 일 자체를 바꾸는 플래그 인자(flag argument)는 피하는 것이 좋다는 조언도 많습니다. PEP 8의 규칙은 아니지만, 플래그에 따라 하는 일이 달라지는 함수는 사실 두 가지 일을 하는 함수이기 때문입니다.

# 플래그 하나로 두 가지 일을 하는 함수
def summarize(values, as_percent=False):
    ...

# 한 가지 일만 하는 함수 두 개
def mean(values):
    ...

def mean_percent(values):
    ...

또 함수의 인자는 적을수록 좋습니다. 인자가 너무 많으면 실수할 가능성이 커지고, 읽는 사람도 “이 함수는 여기서는 이것을 받다가 왜 저기서는 또 이상한 인자를 받지?” 하고 헷갈리게 됩니다. 마지막으로, 함수는 되도록 바깥의 전역 변수를 바꾸지 않아야 합니다. 함수가 입력을 받아 결과를 돌려주는 것 외에 바깥 상태를 몰래 바꾸는 것을 부작용(side effect)이라고 하는데, 부작용이 있는 함수는 실행 순서에 따라 결과가 달라져서 지난 글의 일관성과 재현성을 해치기 쉽습니다.

줄 맞춤

소스 코드에는 공백, 들여쓰기, 빈 줄 같은 공백 문자(whitespace)가 아주 많은데, 이것들이 중구난방이면 읽기 어렵습니다. PEP 8은 다음과 같은 관례를 제시합니다.

  1. 들여쓰기는 공백 4칸으로 합니다. 탭 문자보다 공백을 권합니다.
  2. 한 줄은 79자를 넘지 않게 씁니다. (독스트링과 주석은 72자) 여러 명령을 한 줄에 몰아넣지 말라는 뜻이기도 합니다.
  3. 맨 바깥의 함수나 클래스를 정의할 때는 위아래로 빈 줄 2개를 두고, 클래스 안의 메서드 사이에는 빈 줄 1개를 둡니다.
  4. 모듈을 불러올 때는 import os, sys처럼 쓰지 말고 한 줄에 하나씩 import os, import sys로 씁니다. (from os import path, sep처럼 한 모듈에서 여러 개를 가져오는 것은 괜찮습니다.)
  5. =, +=, ==, < 같은 대입 연산자와 비교 연산자의 앞뒤에는 공백을 한 칸씩 둡니다. +, * 같은 산술 연산자는 보통 앞뒤에 공백을 두되, x = x*2 - 1처럼 우선순위가 높은 연산자의 공백을 생략해 계산 순서를 드러내는 것도 허용합니다.
  6. 함수를 호출하거나 정의할 때 인자에 =를 쓰는 경우에는 앞뒤에 공백을 두지 않습니다. 예를 들어 plot(x, y, color='red')처럼 씁니다.

주석

주석에도 관례가 있습니다.

  1. 주석이 코드와 모순되면 안 됩니다. 코드를 고쳤다면 주석도 함께 고쳐야 합니다. 틀린 주석은 주석이 없는 것보다 나쁩니다.
  2. 주석은 완전한 문장으로 씁니다. (영어라면 첫 글자를 대문자로 씁니다.)
  3. 주석은 # 뒤에 한 칸을 띄우고 씁니다. 코드와 같은 줄에 쓰는 주석은 코드와 최소 두 칸 떨어뜨립니다.
  4. 독스트링은 첫 줄에 한 줄짜리 요약을 쓰고, 빈 줄을 하나 둔 다음 자세한 설명을 씁니다. 이 관례는 PEP 8에서 이어지는 독스트링 전용 문서인 PEP 257에 정리되어 있습니다.2

그런데 주석과 문서화(documentation)의 차이가 헷갈릴 수 있습니다. 예를 들어 주피터 노트북에서는 코드 셀 안에 주석을 쓸 수도 있고, 코드 셀 밖의 마크다운 셀에 설명을 쓸 수도 있는데, 마크다운 셀에 쓰는 것이 문서화에 해당합니다. 문서화는 코드의 원리와 목적뿐 아니라 사용자에게 이 코드를 어떻게 쓰는지까지 자세히 설명하는 것이고, 주석은 다른 개발자에게 왜 여기서 이 코드를 쓰며 여기서 무슨 일이 일어나는지를 알려 주는, 딱 코드 차원의 설명입니다.

문서화는 설명하고 싶은 방식대로 자유롭고 친절하게 쓰면 되지만, 주석은 간결해야 합니다. 주석이 길다는 것은 그 코드를 왜 쓰는지, 목적이 무엇인지를 말로 주절주절 설명해야 한다는 뜻이고, 이것은 그 코드가 깔끔하게 짜여 있지 않다는 신호입니다. 나쁜 코드를 주석으로 때우려 하기보다는, 코드를 잘 짜서 주석을 줄이는 방향을 목표로 해야 합니다. 잘 짠 코드는 주석이 거의 필요 없습니다.

포매터와 린터

관례가 참 많지요? 코드를 쓰면서 이걸 전부 지키겠다고 하면 말리지는 않겠지만, 사실 거의 불가능에 가깝습니다. 사람마다 프로그래밍을 배운 경로와 경험이 다르니 저마다 버릇이 있기 마련이고, 갑자기 PEP 8을 100퍼센트 완벽하게 지키라는 것은 현실적이지 않습니다. 그래서 이런 일을 자동으로 해 주는 도구들이 있습니다.

  • 포매터(formatter)는 코드의 모양을 자동으로 고쳐 줍니다. 공백, 줄바꿈, 따옴표 같은 것을 일관된 스타일로 바꿉니다. 대표적으로 black, autopep8, yapf가 있습니다.
  • 린터(linter)는 코드를 실행하지 않고 읽어서 문제가 될 만한 곳을 찾아 알려 줍니다. 스타일 위반뿐 아니라, 쓰지 않는 import, 정의되지 않은 변수 같은 작은 실수나 나쁜 버릇도 잡아냅니다. 대표적으로 flake8, pylint, pyflakes가 있고, 자료형이 맞는지를 검사하는 mypy 같은 타입 검사기도 비슷한 역할을 합니다.
  • 요즘에는 포매터와 린터의 기능을 한데 모은 ruff도 많이 씁니다.

이런 도구들은 보통 VS Code 같은 편집기나 주피터에 연결해서, 파일을 저장할 때마다 자동으로 포매팅하고 문제를 표시하도록 설정해 씁니다. 포매터로 모양을 맞추고 린터로 실수를 잡는 조합으로, PEP 8을 점검하는 동시에 오류와 잠재적인 오류까지 잡아낼 수 있습니다. 직접 해 보겠습니다. 설치는 3.9에서 다룰 pip으로 합니다.

AI가 짠 코드를 받아들이기 전에

여러 번 이야기했듯이, 이제 우리는 직접 코드를 쓰는 것 이상으로 AI가 만든 코드를 씁니다. 우리는 코드를 만드는 사람이라기보다, AI가 만든 코드를 검수하고, 보완하고, 이해하고, 방어해서 결과물을 만드는 사람에 가깝습니다. 그러니 AI가 만든 코드를 어떻게 대할지도 고민해 둘 필요가 있습니다.

방법은 간단합니다. AI가 만든 코드를, 나보다 실력이 조금 부족한(?) 후배가 “선배님, 이런 코드는 어떨까요?” 하고 내민 제안이라고 생각하면 됩니다. 그러면 우리는 그 제안을 받아들일지 말지를 정해야 하는데, 받아들이기 전에 다음을 스스로 물어봐야 합니다.

  1. 이 코드의 모든 줄을 내가 설명할 수 있는가?
  2. 내가 고른 입력에 대해 이 코드가 어떤 결과를 낼지 미리 예측할 수 있는가?
  3. 이 코드가 데이터에 대해 암묵적으로 깔고 있는 가정을 찾아낼 수 있는가? (예를 들어 결측치가 없다거나, 날짜가 정렬되어 있다거나)
  4. 시간이 충분했다면 나도 비슷하게 접근했을까?

이 가운데 하나라도 “아니오”라면, 그 코드는 분석에 넣지 않는 것이 좋습니다. AI의 제안을 받아들이는 것은 꽤 책임이 따르는 일입니다. 제안을 받아들인 순간부터 그 코드는 내 코드입니다. 나중에 문제가 생겼을 때 “이건 제가 쓴 게 아니라 클로드가 짜 준 거예요!”라는 변명은 통하지 않습니다. AI가 코드를 만드는 데는 클릭 한 번이면 되니 별것 아닌 것처럼 느껴질 수 있지만, 문제가 생겼을 때 책임을 지는 것은 AI가 아니라 나입니다.

AI 코드에서 자주 보이는 오류

AI는 대중의 뜨거운 관심에 비해 아직 완벽하지 않습니다. AI가 만든 코드에서는 다음과 같은 오류가 자주 나옵니다.

  1. API 환각(API hallucination): 존재하지 않는 함수나 인자, 혹은 다른 라이브러리의 함수를 그럴듯하게 지어내서 씁니다.
  2. 그럴듯하지만 틀린 기본값: 표본 표준편차를 구해야 하는데 모집단 표준편차를 구하는 함수를 쓰거나, 결측치가 얼마나 있든 조용히 무시하고 계산하는 식입니다.
  3. 오류에 침묵하기: 일단 돌아가는 코드를 만들려는 경향 때문에 try-except를 도배하는 경우가 있는데, 그러면 진짜 버그가 있는 곳에서도 오류가 삼켜져서 결과에 버그가 그대로 반영되고, 나중에 디버깅하기도 어려워집니다.
  4. 미묘한 통계적 오류: 전체 데이터가 아니라 일부 그룹으로만 통계량을 계산하거나, 학습 데이터와 테스트 데이터를 섞어 쓰거나, 배열의 축을 잘못 지정하는 식입니다.
  5. 낡은 패턴: 예전에는 쓸 수 있었지만 지금은 없어졌거나 쓰지 말라고 권하는 함수나 라이브러리를 씁니다.

물론 요즘에는 1번이랑 5번은 거의 없습니다. 하지만 나머지 오류들은 아직 건재?합니다. 이런 오류들은 코드를 그냥 읽기만 해서는 눈치채기 어렵습니다. 2번이 얼마나 눈에 안 띄는지 직접 보겠습니다. 같은 데이터의 표준편차를 넘파이와 판다스로 각각 구해 보겠습니다.

import numpy as np
import pandas as pd

heights = [172.0, 165.0, 181.0, 158.0, 175.0]
print("넘파이 np.std   :", np.std(heights))
print("판다스 Series.std:", pd.Series(heights).std())
넘파이 np.std   : 7.984985911070852
판다스 Series.std: 8.927485648266257

같은 데이터인데 값이 다릅니다. 둘 다 오류 없이 실행되었으니, 코드만 봐서는 어느 쪽이 맞는지 알 수 없습니다. 2.2에서 보았듯이 분산을 구할 때 \(n\)으로 나눌 수도, \(n-1\)로 나눌 수도 있는데, 넘파이의 np.std는 기본으로 \(n\)으로 나누고, 판다스의 std는 기본으로 \(n-1\)로 나누기 때문입니다. 표본에서 모집단의 분산을 추정하려는 것이라면 \(n-1\)로 나누는 쪽이 맞고, 넘파이에서는 ddof=1을 직접 적어 줘야 합니다.

print("넘파이 np.std(ddof=1):", np.std(heights, ddof=1))
넘파이 np.std(ddof=1): 8.927485648266257

결측치도 마찬가지입니다. 측정값 하나가 빠져서 NaN(Not a Number)으로 들어 있다고 해 보겠습니다.

heights_with_nan = [172.0, 165.0, np.nan, 158.0, 175.0]
print("넘파이 np.mean   :", np.mean(heights_with_nan))
print("판다스 Series.mean:", pd.Series(heights_with_nan).mean())
print("판다스 결측치 개수:", pd.Series(heights_with_nan).isna().sum())
넘파이 np.mean   : nan
판다스 Series.mean: 167.5
판다스 결측치 개수: 1

넘파이는 결측치가 하나라도 있으면 결과를 nan으로 내서 무언가 이상하다는 것을 알려 주지만, 판다스는 결측치를 조용히 빼고 나머지 4개로 평균을 냅니다. 편리할 때도 있지만, 결측치가 절반이라면 이야기가 달라집니다. 어떤 값이 몇 개나 빠졌는지 모른 채로 평균을 보고하면, 1.4에서 본 것 같은 편향이 생길 수 있습니다.

그래서 데이터 사이언티스트들은 AI가 만든 코드를 그냥 믿지 않고, 지난 글에서 말한 것처럼 정답을 아는 토이 데이터를 넣어서 정말 잘 동작하는지 확인하거나, 코드를 작은 단위로 쪼개서 하나하나 시험하는 단위 테스트(unit test)로 이런 오류를 잡아냅니다. 단위 테스트는 3.10에서 다룹니다.

정리

  • 파이썬의 철학인 The Zen of Python은 단순하고 명확하며 읽기 좋은 코드를 추구합니다.
  • PEP 8은 파이썬 코드의 스타일 가이드입니다. 클래스는 CapWords, 함수와 변수는 snake_case, 상수는 대문자로 쓰고, 들여쓰기는 공백 4칸, 한 줄은 79자 이내로 씁니다.
  • 이름은 뜻이 드러나게, 일관되게 짓고, 매직 넘버에는 이름을 붙입니다. 함수는 한 가지 일만 하게 짭니다.
  • 포매터는 코드의 모양을, 린터는 문제가 될 만한 곳을 자동으로 찾아 줍니다. 이름 짓기처럼 내용에 관한 것은 사람이 정해야 합니다.
  • AI가 짠 코드는 후배의 제안처럼 대하고, 모든 줄을 설명할 수 있는지, 결과를 예측할 수 있는지, 숨은 가정은 무엇인지 확인한 뒤에 받아들입니다. 받아들인 코드는 내 코드입니다.

지금까지 좋은 코드를 쓰는 법을 이야기했는데, 좋은 코드도 계속 고쳐지다 보면 어느 버전으로 어떤 결과를 냈는지 헷갈리기 시작합니다. 다음 글에서는 이 문제를 해결하는 버전 관리와 깃을 다룹니다.
