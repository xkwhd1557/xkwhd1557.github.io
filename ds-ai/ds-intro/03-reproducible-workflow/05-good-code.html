3.5 좋은 코드란 무엇일까요?

3장 재현 가능한 작업 환경 · AI 시대의 코딩과 문학적 프로그래밍

데이터 사이언스·AI
데이터 사이언스 개론
가독성, 재현성, 일관성, 정확성, 재사용성, 견고함이라는 좋은 코드의 여섯 가지 성질을 예제와 함께 살펴보고, AI가 코드를 쓰는 시대에 이 성질들이 왜 더 중요해졌는지, 그리고 코드를 사람이 읽는 글처럼 쓰자는 크누스의 문학적 프로그래밍을 소개합니다.
Published

November 4, 2026

들어가며

3.4까지는 배쉬로 데이터를 다루는 법을 살펴보았습니다. 이번 글과 다음 글에서는 잠시 데이터에서 한 걸음 물러나서, 코드 자체에 대한 이야기를 해 보려고 합니다.

프로그래밍을 하는 방법에는 정답이 없습니다. 언어의 문법을 지키고 알맞은 알고리즘만 짜면, 나머지는 각자 마음대로 써도 프로그램은 돌아갑니다. 하지만 너무 자유분방하게 쓴 코드는 쓴 사람만, 심하면 쓴 사람조차 나중에 알아보지 못한다는 치명적인 단점이 있습니다.

데이터 사이언스에서는 이 문제가 특히 심합니다. 데이터 자체가 지저분하고 복잡하다 보니, 그것을 다루는 코드도 복잡해지기 쉽기 때문입니다. 그래서 누가 보더라도 쉽게 이해할 수 있는 깔끔한 코드를 쓰는 것이 중요합니다. 이번 글에서는 먼저 “좋은 코드”가 갖춰야 할 성질들을 정리하고, AI가 코드를 대신 써 주는 시대에 이 성질들이 왜 더 중요해졌는지 살펴본 다음, 이 생각을 오래전에 하나의 철학으로 정리한 문학적 프로그래밍(literate programming)을 소개하겠습니다.

좋은 코드의 여섯 가지 성질

가독성

가장 기본적인 좋은 코드의 성질은 가독성입니다. 정확히는 이해 가능성(comprehensibility)이라고 하는 편이 더 맞습니다. 좁은 의미의 가독성(readability)이 코드가 깔끔하고 보기 좋게 쓰였는지를 뜻한다면, 이해 가능성은 거기서 더 나아가 그 코드가 결과를 만들어 내는 과정을 다른 사람도 쉽게 이해할 수 있는지를 뜻합니다. 한국어로는 가독성이라는 말이 더 입에 붙으니, 이 글에서는 가독성을 이 넓은 의미로 쓰겠습니다.

데이터 사이언스의 과제는 다른 과학·공학 분야처럼 여러 사람이 함께 수행합니다. 그래서 나만 아는 비밀스러운 방법보다는, 같은 지식을 가진 사람이라면 누구나 이해하고 고칠 수 있는 코드를 쓰는 것이 좋습니다. 혼자 하는 과제라도 마찬가지입니다. 지금 쓴 코드를 내년에 다시 보면, 이것이 무엇을 하는 코드이고 왜 필요했는지 기억나지 않을 수 있습니다.

가독성을 높이는 가장 간단하면서도 어려운 방법은 주석(comment)과 독스트링(docstring)입니다. 주석은 컴퓨터는 무시하고 사람만 읽는 코드 속의 설명이고, 독스트링은 파이썬에서 함수나 클래스의 첫 줄에 문자열로 적어 두는 설명입니다. help() 함수로 어떤 함수를 찾아보면 나오는 설명이 바로 독스트링입니다.

help(print)

우리가 직접 만든 함수에도 독스트링을 달아 두면, 다른 사람이 help()로 같은 설명을 볼 수 있습니다.

def sample_mean(values):
    """표본 평균을 계산합니다.

    values는 숫자들이 들어 있는 리스트입니다.
    빈 리스트가 들어오면 ZeroDivisionError가 발생합니다.
    """
    return sum(values) / len(values)

help(sample_mean)

sample_mean(values)
    표본 평균을 계산합니다.

    빈 리스트가 들어오면 ZeroDivisionError가 발생합니다.

주석과 독스트링을 어떻게 쓸지에 대해서는 언어 차원의 강제 규칙이 없습니다. 다음 글에서 보듯이 권장되는 관례는 있지만 반드시 지켜야 하는 것은 아니고, 실제로도 많은 프로그래머가 누구나 이해할 수 있는 선에서 자기만의 방식으로 씁니다.

그렇다면 모든 과정을 주석으로 하나하나 다 설명하면 가장 이해하기 쉬울까요? 그렇지 않습니다. 오히려 주석을 달 때 피해야 하는 방법 가운데 하나입니다. 모든 줄에 설명을 달면 각 줄을 이해하기는 쉬울지 몰라도, 코드 전체의 구성이 눈에 들어오지 않아 오히려 읽기 어려워집니다. 그래서 주석의 양과 코드의 깔끔함 사이에서 적절히 줄다리기를 해야 합니다. 코드는 그 자체로 읽기 좋게 쓰고, 주석은 꼭 필요한 곳에만 다는 것이 목표입니다.

주피터 노트북으로 분석 코드와 보고서를 쓸 때는 이 줄다리기가 더 쉽습니다. 주피터에는 코드를 적는 코드 셀과 글을 적는 마크다운 셀이 따로 있으니, 코드 셀의 주석에는 정말 필요한 것만 남기고, 각 단계의 설명은 마크다운 셀에 글로 쓰면 되기 때문입니다.

그렇다고 코드에 개성을 담지 말라는 뜻은 아닙니다. 저와 같은 세대의 한국 학생이라면 이스터 에그(easter egg)라는 말을 리그 오브 레전드 같은 게임에서 처음 들어 보셨을 텐데, 이스터 에그는 개발자가 몰래 숨겨 둔 기능이나 메시지를 뜻합니다. 프로그램 전체의 흐름에는 별 영향이 없지만, 개발자만 존재를 아는 장난 같은 것입니다. 프로그래머들은 자기 코드를 일종의 작품으로 여겨서 이런 것을 넣어 두기도 합니다.

얼핏 생각하면 이스터 에그는 “나만 알아보는 코드”라서 좋은 코드와 거리가 멀어 보이지만, 꼭 그렇지는 않습니다. 이스터 에그는 보통 두 가지 방식으로 남깁니다. 하나는 주석에 자기만의 말투를 섞거나 프로그래머로서의 서명을 남기는 것인데, 이 정도는 이해 가능성을 해치지 않습니다. 다른 하나는 숨겨진 기능인데, 이것도 원래 목표한 기능은 모두 제대로 하면서 (예를 들어 홈 버튼을 99번 연달아 누르면 이모티콘이 뜨는 것처럼) 없어도 그만인 기능을 하나 더 얹는 것이라서, 너무 많이 넣지만 않는다면 큰 문제가 되지 않습니다.

재현성

가독성만큼 중요한 것이 3장 소개 글에서 이야기한 재현성(reproducibility)입니다. 데이터 사이언스는 결과의 진위가 불확실한 결론을 내놓기 때문에, 누구나 같은 데이터로 같은 결과를 다시 얻을 수 있도록 코드를 써야 합니다.

그런데 재현성의 의미가 일반적인 소프트웨어 개발과 데이터 사이언스에서 조금 다릅니다. 일반 프로그래밍에서 재현성은 “같은 환경이라면 코드가 늘 오류 없이 똑같이 실행되는가(결정론적 동작)”, 그리고 “다양한 환경에서도 잘 돌아가는가(호환성)”의 문제입니다. 반면 데이터 사이언스는 데이터로 가설을 검증하고 통계적 예측을 하는 과학 연구에 가깝습니다. 결과물의 진위나 모델의 성능이 데이터와 알고리즘의 상태에 따라 매번 달라질 수 있습니다. 그래서 데이터 사이언스에서의 재현성은 누가 어떤 환경에서 같은 데이터와 코드를 돌리더라도, 원래 분석과 똑같은 결론과 모델 성능을 얻을 수 있는가를 뜻합니다.

데이터 사이언스에서 재현성이 깨지는 가장 대표적인 원인은 난수입니다. 머신러닝 등에서는 데이터를 무작위로 섞거나 나누는 등 난수를 쓰는 과정이 자주 나오는데, 이 무작위성 때문에 내 컴퓨터에서는 훌륭했던 모델이 다른 사람의 컴퓨터에서는 기대에 못 미칠 수도 있습니다.

2.4에서 보았듯이 컴퓨터가 만드는 난수는 진짜 무작위가 아니라, 시드(seed)라는 값에서 출발해 정해진 계산 규칙으로 만들어지는 유사 난수(pseudo-random number)입니다. 그래서 같은 시드에서 출발하면 같은 숫자가 같은 순서로 나옵니다.

import numpy as np

np.random.seed(1557)
print(np.random.rand(3))
print(np.random.rand(3))   # 이어서 뽑으면 다른 숫자가 나옵니다.

np.random.seed(1557)       # 시드를 다시 같은 값으로 정하면
print(np.random.rand(3))   # 처음과 똑같은 숫자가 나옵니다.
[0.56431542 0.89729768 0.43135233]
[0.12878063 0.25565071 0.95145538]
[0.56431542 0.89729768 0.43135233]

시드를 공유하면 누구나 같은 난수를 뽑아 같은 과정을 반복할 수 있습니다. 그래서 데이터 사이언스에서는 시드를 코드에 명시적으로 적어 두는 것이 권장됩니다.

또 데이터 사이언스에서는 모델을 계속 고쳐 나가는데, 그 과정을 누구나 알 수 있어야 합니다. 이것도 재현성의 일부이고, 3.7에서 다룰 깃을 이용한 버전 관리로 해결할 수 있습니다. 흔히 듣는 깃허브(GitHub)는 이 버전 관리를 인터넷에 공개된 곳에서 할 수 있게 해 주는 서비스입니다.

일관성

논리적인 연결이 빈틈없고 실행 흐름이 분명한 코드를 일관성(consistency) 있는 코드라고 합니다. 코드를 실행했을 때 처음부터 끝까지 막힘없이 결과가 나오고, 코드가 어떤 순서로 무엇을 하는지 예측할 수 있어야 한다는 뜻입니다. 데이터 분석이라면 데이터를 불러오고, 전처리하고, 분석하거나 모델을 만들고, 결과를 시각화해서 전달하는 과정이 뒤죽박죽 얽히지 않고 순서대로 잘 정리되어 있어야 합니다.

주피터 노트북은 셀을 아무 순서로나 실행할 수 있어서 이 일관성이 깨지기 쉽습니다. 위쪽 셀을 고치고 아래쪽 셀만 다시 실행하다 보면, 노트북에 보이는 코드와 실제로 메모리에 있는 상태가 달라집니다. 그래서 노트북으로 작업한 뒤에는 커널을 재시작하고 처음부터 끝까지 한 번에 실행해서 같은 결과가 나오는지 확인하는 습관이 좋습니다.

일관성을 지키는 데에도 버전 관리가 큰 도움이 됩니다. 어제는 잘 돌던 코드가 오늘 갑자기 이상한 결과를 낸다면, 코드의 변경 이력을 거슬러 올라가 무엇이 바뀌었는지 찾아낼 수 있어야 합니다. 여기에 더해 데이터베이스(database)를 쓸 수도 있습니다. 데이터베이스는 간단히 말해 데이터를 정해진 규칙에 따라 정리해서 모아 두는 곳인데, 내 컴퓨터 여기저기에 흩어진 파일들을 쓰는 대신 데이터베이스에서 데이터를 불러오면 데이터의 형태와 구조가 일관되게 유지되고, 순서가 꼬이거나 데이터가 사라지는 일을 막을 수 있습니다. 데이터베이스는 이 과목의 뒷부분에서 다시 다룹니다.

정확성

당연히 코드는 정확(correctness)해야 합니다. 코드와 그 코드가 구현하는 분석 과정이, 우리가 목표한 과제를 오류 없이 제대로 해결해야 한다는 뜻입니다.

이 당연한 이야기를 굳이 하는 이유는, 데이터 사이언스에서는 정확한지 확인하는 것 자체가 어렵기 때문입니다. 앱이나 간단한 게임을 만드는 일반적인 개발이라면, 오류 없이 실행되고 의도한 기능이 잘 동작하면 됩니다. 그런데 데이터 분석에서 결과가 이상하다면, 분석 방법이 잘못된 것인지, 데이터가 잘못된 것인지, 코드가 잘못된 것인지를 모두 따져 봐야 합니다. 게다가 결과가 일단 나오기만 하면, 그것이 정말 좋은 결과인지 잘못된 결과인지 판단하기 어려운 경우도 많습니다.

그래서 데이터 사이언스에서는 토이 데이터(toy data)를 자주 씁니다. 정답을 이미 알고 있는 작은 데이터를 일부러 만들어서 분석에 넣어 보는 것입니다. 예를 들어 기울기가 정확히 2인 직선 위에 점들을 만들어 회귀 분석 코드에 넣었는데 기울기가 2가 나오지 않는다면, 데이터가 아니라 코드에 문제가 있다는 것을 알 수 있습니다. 이렇게 결과를 정답과 비교하면서 문제가 어디에 있는지 좁혀 나갑니다. 널리 쓰이는 기준 데이터로 성능을 비교하는 벤치마크(benchmark)도 같은 생각입니다. 이런 확인을 자동으로 하는 방법은 3.10의 단위 테스트에서 다룹니다.

재사용성

재사용성(reusability)은 내가 쓴 코드의 일부(데이터 처리 과정, 특정 함수, 모델링 과정 등)를 떼어서, 비슷한 맥락의 새로운 분석에 다시 쓸 수 있어야 한다는 성질입니다. 재현성이 같은 결과를 다시 얻는 것이라면, 재사용성은 같은 코드를 다른 곳에 다시 쓰는 것입니다.

솔직히 말하면, 이 성질은 앞의 성질들에 비해 “있으면 좋고, 없어도 크게 나쁘지는 않은” 성질처럼 느껴질 수 있습니다. 그런데 재사용성을 강조하는 진짜 이유는, 정말로 다른 프로젝트에 가져다 쓰라는 것보다는 코드를 잘 쪼개서(모듈화해서) 쓰라는 데 있다고 생각합니다. 재사용성이 전혀 없는 코드를 떠올려 보면, 데이터 파일의 경로나 파라미터 같은 것들이 코드 곳곳에 지금 당장의 상황에 맞게 박혀 있는 경우가 많습니다. 이런 코드는 새로운 데이터가 들어오면 여기저기를 다 고쳐야 합니다. 반대로 기능별로 함수를 나누고 바뀔 수 있는 값들을 한곳에 모아 두면, 새 데이터가 들어오거나 무언가를 고칠 때 훨씬 깔끔하게 대응할 수 있습니다. 그렇게 보면 재사용성도 꽤 중요한 성질입니다.

견고함

마지막 성질은 견고함(robustness)입니다. 수치 해석을 공부해 보신 분이라면 익숙한 말일 텐데, 수치 알고리즘 중에는 입력이 조금만 달라져도 결과가 크게 달라지는 것이 많습니다. 데이터를 다루는 코드도 데이터셋이 조금만 바뀌면 결과가 크게 달라지거나 멈춰 버릴 수 있습니다. 견고함은 새로운 데이터셋이 들어오거나 파라미터가 바뀌어도 코드가 쉽게 깨지지 않고 버티는 성질입니다.

이를 위해 파이썬에서는 예외(exception)를 쓸 수 있습니다. 데이터가 꼭 만족해야 하는 조건을 확인하고, 조건이 깨지면 조용히 넘어가는 대신 분명한 오류를 내도록 하는 것입니다. 예를 들어 나이 데이터에 음수가 들어 있다면 무언가 잘못된 것이니, 평균을 계산하기 전에 멈추게 할 수 있습니다.

def mean_age(ages):
    """나이들의 평균을 계산합니다. 음수인 나이가 있으면 ValueError를 냅니다."""
    if len(ages) == 0:
        raise ValueError("나이 데이터가 비어 있습니다.")
    if min(ages) < 0:
        raise ValueError(f"음수인 나이가 있습니다: {min(ages)}")
    return sum(ages) / len(ages)

print(mean_age([23, 31, 27]))
print(mean_age([23, -5, 27]))
27.0
ValueError: 음수인 나이가 있습니다: -5

이상한 값을 그냥 빼고 계산을 이어 가도록 코드를 짤 수도 있지만, 그렇게 할 때는 몇 개를 왜 뺐는지를 반드시 기록으로 남겨야 합니다. 조용히 빼 버리면 결과가 틀려도 아무도 눈치채지 못하기 때문입니다.

AI 시대에 이 성질들이 더 중요해진 이유

위의 성질들은 꽤 오래전부터 좋은 코드의 조건으로 이야기되어 왔습니다. 그런데 AI가 코드를 대신 써 주는 요즘, 이 성질들은 오히려 훨씬 더 중요해졌습니다. “어차피 AI가 다 짜 주는데 무슨 상관이야?”라고 생각할 수 있지만, 그렇지 않습니다.

AI가 코드를 쓰는 일의 상당 부분을 대신할 수 있게 된 것은 사실입니다. 코드를 쓰는 비용은 아주 싸졌습니다. 하지만 코드를 읽고 검증하는 비용은 전혀 싸지지 않았습니다. 간단한 코드라면 AI도 잘 설명하지만, 여러 데이터를 엮어 분석하는 복잡한 코드가 정말 맞는지는 결국 사람이 따져 봐야 하는 경우가 많습니다. 애초에 우리는 사람이 쓰기 위해서 코드를 작성하는거니까요. AI는 아직 코드를 써 주는 조수이지, 그 코드를 책임지고 검토해 주는 독자는 아닌 것입니다.

그래서 프로그래머의 역할도 바뀌고 있습니다. 예전에는 코드를 만들어 내는 것이 주된 일이었다면, 이제는 AI가 만든 코드를 읽고, 검증하고, 책임지는 일이 더 중요해졌습니다. 위에서 “다른 사람이 이해하고 재현할 수 있어야 한다”고 한 성질들이 결국 나 자신을 위한 것이 된 셈입니다. 코드를 AI가 썼다면, 그 코드를 가장 먼저 이해하고 재현할 수 있어야 하는 사람은 바로 나니까요.

이제 코드는 데이터로 무엇을 했는지를 보여 주는 기록입니다. 그 기록을 읽지 못한다면 결과가 맞는지 판단할 수도, 다른 사람의 질문에 결과를 방어할 수도 없습니다. 데이터 사이언티스트, 더 넓게는 프로그래머의 목표가 “잘 돌아가는 코드를 쓰라”에서 “내가 설명하고 방어할 수 있는 코드를 (AI의 도움을 받아서라도) 만들어 내라”로 바뀌었다고 할 수 있습니다.

AI 때문에 개발자의 일자리가 줄고 있다는 이야기를 많이 듣는데, 그럴수록 우리가 설 자리는 결국 코드를 잘 이해하고 결과물을 검증하는 능력에서 나옵니다. 그리고 그 능력의 바탕은 코드를 단순히 쓰는 기술이 아니라, 그 코드 뒤에 있는 아이디어를 이해하는 것입니다. AI 때문에 이런 기초 지식이 쓸모없어졌다고 말하는 사람도 많지만, 저는 반대라고 생각합니다. AI가 아무리 지식을 알려 줘도, 그 지식을 이해하고, AI가 짠 코드의 원리를 파악하고, 이리저리 고쳐서 쓸 만한 결과물로 만들어 내는 것은 결국 사람이니까요.

위의 성질들 가운데 가장 중요한 것을 꼽으라면 가독성과 재현성입니다. 재현성은 3.7부터 본격적으로 다루기로 하고, 여기서는 가독성을 하나의 철학으로 정리한 문학적 프로그래밍을 살펴보겠습니다.

문학적 프로그래밍

지금까지 “좋은 코드”의 성질이라고 했지만, 데이터 사이언스의 관점에서 보면 이것은 사실 좋은 데이터 분석의 성질이기도 합니다. 좋은 분석은 다른 사람이 그 과정을 이해할 수 있어야 하고, 재현할 수 있어야 하며, 새로운 결과를 만드는 데 통찰을 줄 수 있어야 합니다. 그 과정의 대부분이 코드로 이루어지기 때문에 좋은 코드의 성질이라고 부르는 것입니다.

이런 생각은 생각보다 오래되었습니다. 컴퓨터 과학에서 전설적인 인물로 꼽히는 도널드 크누스(Donald Knuth)라는 사람이 있습니다. 알고리즘 분야의 고전으로 꼽히는 『컴퓨터 프로그래밍의 예술』(The Art of Computer Programming)의 저자이고, 수학 문서를 쓸 때 거의 표준처럼 쓰이는 조판 시스템 TeX을 만든 사람이기도 합니다. 크누스는 1984년의 논문에서 문학적 프로그래밍(literate programming)이라는 생각을 제안했습니다.1

그때까지 프로그래밍은 기계가 이해하기 좋은 순서와 구조로 명령을 적어서 넘겨주는 일로 여겨졌습니다. 크누스는 이 생각을 뒤집었습니다. 프로그램을 쓸 때 우리의 주된 일은 컴퓨터에게 무엇을 하라고 지시하는 것이 아니라, 컴퓨터가 무엇을 하기를 원하는지를 사람에게 설명하는 것이라고 보자는 것이었습니다. 프로그램의 중심에 컴퓨터를 위한 명령이 아니라, 그 작업을 하려는 사람의 논리적인 생각의 흐름과 그 생각들이 거미줄(web)처럼 얽힌 설명이 와야 한다는 것입니다.

크누스는 이 철학을 주장하는 데 그치지 않고, 실제로 WEB이라는 시스템을 만들었습니다. WEB으로 쓰는 파일에는 사람이 읽는 설명과 컴퓨터가 실행할 코드 조각이 에세이처럼 한데 섞여 있습니다. 코드 조각은 컴퓨터가 실행하기 좋은 순서가 아니라, 사람이 이해하기 좋은 순서로 배치됩니다. 그리고 이 파일 하나에서 두 가지 결과물을 뽑아냅니다. 하나는 tangle이라는 도구로 코드 조각들을 실행 순서대로 엮어 낸 프로그램이고, 다른 하나는 weave라는 도구로 설명과 코드를 보기 좋게 짜 낸 문서입니다. 이 문서를 아름답게 인쇄하는 데 쓰인 것이 바로 TeX이었습니다.

이렇게 프로그램을 소스 코드 하나로 끝내는 대신, 에세이나 문학 작품을 쓰듯 사람의 언어와 코드가 조화롭게 어우러지도록 쓰자는 철학이 문학적 프로그래밍입니다. 위에서 다룬 성질들 가운데 가독성, 그것도 넓은 의미의 이해 가능성을 가장 중요하게 여기는 철학이지요.

이 철학은 AI 시대에 더 중요해졌습니다. 앞에서 말했듯이 이제 우리의 일은 AI로 코드를 만들고, 그것을 고치고, 해석하고, 방어하는 것인데, 문학적 프로그래밍을 따르면 그 과정 전체를 하나의 보고서나 에세이처럼 남길 수 있기 때문입니다.

이 철학이 구체적으로 구현된 것이 바로 우리가 당연하게 쓰고 있는 주피터 노트북입니다. R 마크다운, 그리고 이 사이트를 만드는 데 쓴 쿼토(Quarto)도 마찬가지입니다. 현대의 데이터 사이언스와 통계에서는 이런 방식이 당연한 것이 되었습니다. 배경 지식과 수식을 글로 설명하고, 데이터를 처리하는 코드를 쓰면서 중간중간 글로 잇고, 마지막에는 결과와 시각화 자료를 해석해서 설명하는 식으로 프로젝트를 정리합니다. 이렇게 코드와 그 설명이 한 문서 안에서 함께 관리되는 것을 자기 문서화(self-documentation)라고도 합니다.

정리

  • 좋은 코드는 가독성(이해 가능성), 재현성, 일관성, 정확성, 재사용성, 견고함을 갖춘 코드입니다.
  • 데이터 사이언스에서는 시드를 명시해 난수를 재현 가능하게 하고, 토이 데이터로 정확성을 확인하며, 예외로 이상한 데이터를 일찍 잡아냅니다.
  • AI가 코드를 쓰는 시대에는 코드를 읽고 검증하고 책임지는 능력이 더 중요해졌고, 그래서 이 성질들이 더 중요해졌습니다.
  • 문학적 프로그래밍은 코드를 사람에게 설명하는 글처럼 쓰자는 크누스의 철학이고, 주피터 노트북과 쿼토 같은 도구가 그 생각을 이어받았습니다.

문학적 프로그래밍이 프로젝트 전체의 가독성에 관한 이야기라면, 다음 글에서는 한 단계 내려가서 코드 한 줄 한 줄의 가독성을 위한 코드 스타일을 살펴보겠습니다.
