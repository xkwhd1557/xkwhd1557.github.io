3.9 가상 환경과 컨테이너

3장 재현 가능한 작업 환경 · 실행 환경을 고정하고 공유하기

데이터 사이언스·AI
데이터 사이언스 개론
같은 코드라도 운영체제와 라이브러리 버전에 따라 결과가 달라질 수 있는 이유를 살펴보고, 파이썬 가상 환경 venv와 requirements.txt로 라이브러리를 고정하는 법, 가상 머신과 컨테이너의 차이, 도커로 주피터 환경을 띄우는 법을 운영체제별로 정리합니다.
Published

November 4, 2026

들어가며

3.7과 3.8에서는 코드와 데이터의 버전을 관리하는 법을 살펴보았습니다. 그런데 깃으로 버전 관리를 아무리 잘해도, 코드가 완전히 재현 가능하지 않을 수 있습니다. 아무리 코드를 잘 짜서 완벽한 모델을 만들어도, 그 코드를 실행할 수 있는 환경이 아니라면 실행조차 되지 않습니다. 또 전혀 고치지 않은 같은 코드라도, 다른 컴퓨터로 옮겨서 실행하면 생각보다 다르게 동작할 수 있습니다. 심지어 내 컴퓨터에서 내가 직접 짠 코드라도, 시간이 지나 라이브러리가 업데이트되면 지금 다시 실행했을 때 결과가 달라질 수 있습니다.

이런 차이를 만드는 것은 주로 컴퓨터의 운영체제, 설치된 라이브러리의 버전, 그리고 하드웨어입니다. 이것들을 통틀어 환경(environment)이라고 합니다. 이번 글에서는 환경이 왜 문제가 되는지 살펴보고, 이 문제를 해결하는 두 가지 도구인 가상 환경과 컨테이너를 다룹니다.

코드는 환경 위에서 돌아갑니다

프로그램이 실행되는 환경은 여러 겹의 껍질로 생각할 수 있습니다. 가장 안쪽에 하드웨어가 있고, 그것을 운영체제의 엔진에 해당하는 커널(kernel)이 감싸고 있습니다. 그 바깥을 우리가 흔히 운영체제라고 부르는 나머지 부분이 감싸고, 그 위에 파이썬 같은 언어와 라이브러리가 올라가며, 우리가 짠 코드는 가장 바깥쪽에 있습니다.

껍질 예
우리의 코드 analysis.py
언어와 라이브러리 파이썬 3.13, 넘파이 2.5, 판다스 3.1
운영체제 우분투, 윈도우, 맥OS
커널 리눅스 커널, 윈도우 NT 커널
하드웨어 CPU, 메모리, GPU

(리눅스에서는 커널과 그 위의 운영체제가 따로 나뉘어 있어서, 같은 리눅스 커널 위에 우분투, 데비안, 페도라 같은 여러 배포판(distribution)이 올라갑니다. 윈도우와 맥OS는 커널과 나머지를 한 회사가 함께 만들어 하나의 운영체제로 배포합니다. 커널은 운영체제의 내부 동작을 총괄하고, 배포판은 커널의 동작을 통해 우리가 지금 보고 있는 GUI 등으로 사용자와 직접 상호작용하여 입출력을 맞는 느낌입니다.)

우리가 코드로 만들어 내는 결과물은 코드만의 결과물이 아니라, 이 환경 전체가 함께 만들어 낸 결과물입니다. 그래서 코드 아래의 껍질 중 하나가 달라지면 코드가 쉽게 깨질 수 있습니다.

가장 이상적인 것은 모두가 똑같은 환경을 쓰는 것이지만, 이것은 현실성이 없습니다. 하드웨어부터 사람마다 다르니까요. 다행히 하드웨어가 다른 것은 요즘에는 대부분 큰 문제가 되지 않습니다. 진짜 문제는 라이브러리입니다. 다른 사람의 컴퓨터에는 다른 버전의 라이브러리가 깔려 있을 가능성이 높고, 같은 컴퓨터에서도 한 프로젝트는 어떤 라이브러리의 옛 버전을, 다른 프로젝트는 새 버전을 써야 하면 버전끼리 충돌이 일어납니다. 물론 버전이 달라도 대부분은 잘 돌아갑니다. 하지만 가끔 그렇지 않을 때는 꽤 치명적인 차이를 만듭니다. 함수의 기본값이 바뀌었는데 오류 없이 다른 결과가 나오는 경우가 특히 위험합니다. 3.6에서 본 넘파이와 판다스의 표준편차 차이처럼, 이런 차이는 코드만 봐서는 알아채기 어렵습니다.

라이브러리는 우리가 직접 짜는 것이 아니라 가져다 쓰는 도구라서 뭐가 그리 문제일까 싶지만, 생각보다 라이브러리가 발목을 잡는 일이 많습니다. 복잡한 작업에는 복잡한 라이브러리가 필요하고, 복잡한 라이브러리는 다른 라이브러리들에 의존하는 경우가 많기 때문입니다. 게임 모드를 설치해 보신 분이라면 아실 텐데, 모드 하나를 깔려면 먼저 이걸 깔고, 그다음에 저걸 깔고, 이런 설정을 하고…를 끝없이 반복하는 중노동을 해야 할 때가 있고, 새 모드가 기존 모드와 충돌할까 봐 전전긍긍하기도 합니다. 라이브러리도 마찬가지입니다.

가상 환경

이런 문제를 해결하기 위해 가장 먼저 쓰는 도구가 가상 환경(virtual environment)입니다. 가상 환경은 말 그대로 컴퓨터의 실제 환경과 분리된, 독립적이고 격리된(isolated) 가상의 환경입니다.

위의 껍질 가운데 하드웨어는 웬만해서는 마음대로 바꿀 수 없지만, 그 위의 운영체제와 라이브러리는 바꿀 수 있습니다. “가상”, “버추얼”이라는 이름이 붙은 도구들은 대부분 하나의 하드웨어 위에서 운영체제나 라이브러리를 다르게 설정해서 쓸 수 있게 해 주는 도구들입니다. 컴퓨터에서 모바일 게임을 하려고 쓰는 앱플레이어를 떠올리면 쉽습니다. 앱플레이어는 윈도우 컴퓨터 안에 안드로이드를 가상으로 만들어 주는 프로그램인데, 이렇게 운영체제까지 통째로 바꿔 주는 도구를 가상 머신(virtual machine)이라고 합니다. 가상 머신은 아래에서 다시 다루고, 먼저 운영체제는 그대로 두고 라이브러리만 분리해 주는 가상 환경을 살펴보겠습니다.

왜 라이브러리를 분리해야 할까요?

가상 환경 없이 컴퓨터에 파이썬을 설치하면, 파이썬과 함께 표준 라이브러리(math, random 같은 기본 모듈)가 설치됩니다. 문제는 넘파이, 판다스처럼 표준 라이브러리에 없는 라이브러리를 pip으로 설치할 때 생깁니다. 가상 환경을 쓰지 않으면 이 라이브러리들은 모두 파이썬이 설치된 곳의 하나의 공용 폴더에 설치됩니다. 이 폴더를 site-packages라고 하는데, 컴퓨터의 모든 프로젝트가 이 폴더를 함께 씁니다.

pip은 라이브러리를 설치할 때 그 라이브러리가 의존하는 다른 라이브러리들도 함께 설치해 주는데, 모두 이 공용 폴더에 들어갑니다. 그래서 프로젝트 A를 위해 어떤 라이브러리의 버전을 올리면, 그 라이브러리를 쓰던 프로젝트 B가 깨질 수 있습니다. 공용 폴더에는 한 라이브러리의 버전이 하나만 있을 수 있기 때문입니다.

가상 환경은 라이브러리를 공용 폴더 대신 프로젝트마다 따로 설치합니다. 프로젝트 A를 위한 라이브러리는 A의 가상 환경에, 프로젝트 B를 위한 라이브러리는 B의 가상 환경에 설치하는 식입니다. 그러면 한 컴퓨터 안에서도 여러 프로젝트가 서로 다른 버전의 라이브러리를 충돌 없이 쓸 수 있고, 다른 컴퓨터에서도 같은 가상 환경을 만들면 되니 재현 가능성도 지킬 수 있습니다.

venv로 가상 환경 만들기

파이썬의 가상 환경 도구 가운데 가장 기본적인 것은 venv입니다. 파이썬 3.3부터 표준 라이브러리에 들어 있어서 따로 설치할 필요가 없습니다. 터미널에서 프로젝트 폴더로 이동한 다음, 다음을 입력하면 가상 환경이 만들어집니다.

python3 -m venv venv
ls
venv

python3 -m venv venv는 “파이썬의 venv 모듈을 실행해서(-m venv), venv라는 이름의 가상 환경을 만들어라”는 뜻입니다. 마지막의 venv는 만들 폴더의 이름이라 다른 이름으로 해도 되지만, venv나 .venv로 짓는 것이 관례입니다. 이것은 프로젝트마다 한 번만 하면 됩니다. 실행하면 프로젝트 폴더에 venv라는 폴더가 생깁니다.

가상 환경을 만들었으면 활성화(activate)해야 합니다. 앞의 명령어는 가상 환경의 폴더를 만들었을 뿐이고, 터미널에게 “이제부터 이 가상 환경을 쓰겠다”고 따로 알려 줘야 합니다. 이 부분은 운영체제와 터미널에 따라 명령어가 조금씩 다릅니다.

  • Windows
  • macOS
  • Linux
  • Android (Termux)

윈도우에는 python3 대신 python으로 설치되는 경우가 많아서, 가상 환경을 만들 때도 python -m venv venv라고 입력합니다. 그리고 가상 환경 안의 실행 파일들이 bin이 아니라 Scripts 폴더에 있어서, 활성화 명령어가 터미널마다 다릅니다.

# 깃 배쉬
source venv/Scripts/activate
# 파워셸
.\venv\Scripts\Activate.ps1
:: 명령 프롬프트(cmd)
venv\Scripts\activate

파워셸에서 “이 시스템에서 스크립트를 실행할 수 없으므로…”라는 오류가 나면, 한 번만 Set-ExecutionPolicy -Scope CurrentUser RemoteSigned를 입력해 내 계정에서 스크립트를 실행할 수 있게 허용한 뒤 다시 시도하면 됩니다. WSL의 우분투에서는 Linux 탭과 같습니다.

source venv/bin/activate

맥의 기본 셸인 zsh에서도 같은 명령어를 씁니다.

source venv/bin/activate

우분투에서 python3 -m venv venv를 했을 때 ensurepip is not available이라는 오류가 나면, 먼저 sudo apt install python3-venv로 venv에 필요한 패키지를 설치해야 합니다.

Termux에서는 먼저 pkg install python으로 파이썬을 설치합니다. 가상 환경을 만들고 활성화하는 명령어는 리눅스와 같습니다.

python -m venv venv
source venv/bin/activate

넘파이나 판다스처럼 C로 만든 부분이 있는 라이브러리는 Termux에서 pip으로 설치하면 시간이 오래 걸리거나 실패할 수 있습니다. 이때는 Termux가 미리 준비해 둔 pkg install python-numpy를 쓰고, 가상 환경을 만들 때 python -m venv --system-site-packages venv처럼 공용 라이브러리도 함께 보이도록 하는 방법이 있습니다.

여기서는 리눅스에서 활성화해 보겠습니다.

source venv/bin/activate
which python pip
/home/user/env-project/venv/bin/python
/home/user/env-project/venv/bin/pip

이제 python과 pip이 가상 환경 안의 것을 가리킵니다. 실제 터미널에서는 활성화하면 명령어를 입력하는 줄 맨 앞에 (venv)가 붙어서, 지금 가상 환경 안에 있다는 것을 알려 줍니다. 이 상태에서 pip install을 하면, 라이브러리가 공용 폴더가 아니라 이 가상 환경에만 설치됩니다. 판다스를 설치해 보겠습니다.

판다스 하나를 설치했는데, 넘파이, python-dateutil, tzdata 같은 라이브러리들이 함께 설치되었습니다. 게다가 tzdata는 판다스가 직접 필요로 하는 것이 아니라 python-dateutil이 필요로 하는 라이브러리입니다(출력의 from python-dateutil>=2.9.0->pandas). 판다스가 이것들에 의존하기 때문입니다. 위에서 말한 “이걸 깔려면 먼저 저걸 깔아야 하는” 관계가 바로 이것입니다. 지금 가상 환경에 설치된 라이브러리와 그 버전은 pip freeze로 볼 수 있습니다.

pip freeze
numpy==2.5.4
pandas==3.1.0
python-dateutil==4.0.0
tzdata==2026.6

requirements.txt로 환경 공유하기

pip freeze의 출력은 그 자체로 이 프로젝트의 라이브러리 목록입니다. 이것을 파일로 저장해 두면, 다른 사람이 똑같은 라이브러리 환경을 만들 수 있습니다. 이 파일의 이름은 관례적으로 requirements.txt라고 짓습니다.

pip freeze > requirements.txt
cat requirements.txt
numpy==2.5.4
pandas==3.1.0
python-dateutil==4.0.0
tzdata==2026.6

3.2의 리다이렉션 >로 출력을 파일에 저장했습니다. 이 파일을 코드와 함께 깃으로 커밋해 두면, 저장소를 받은 사람은 자기 컴퓨터에 가상 환경을 만들고 다음 한 줄로 같은 버전의 라이브러리를 설치할 수 있습니다.

pip install -r requirements.txt

3.7의 .gitignore에서 venv/ 폴더를 무시하라고 적어 둔 이유가 여기에 있습니다. 가상 환경 폴더 자체는 운영체제와 파이썬 설치 위치에 묶여 있어서 다른 컴퓨터로 옮겨도 제대로 동작하지 않고 용량도 큽니다. 그래서 폴더 대신 설치 목록인 requirements.txt만 공유하고, 가상 환경은 각자의 컴퓨터에서 새로 만듭니다.

작업이 끝나면 가상 환경을 비활성화합니다. 그래야 나중에 다른 프로젝트의 가상 환경을 쓰거나 공용 폴더에 무언가를 설치할 때 헷갈리지 않습니다.

deactivate
which python3
/usr/local/bin/python3

venv는 어떻게 동작할까요?

가상 환경이 어떻게 라이브러리를 분리하는지 이해하려면, venv 폴더 안을 보면 됩니다.

ls venv
ls venv/bin
cat venv/pyvenv.cfg
bin  include  lib  lib64  pyvenv.cfg
Activate.ps1  activate.csh   f2py          pip   pip3.13  python3
activate      activate.fish  numpy-config  pip3  python   python3.13
home = /usr/local/bin
include-system-site-packages = false
version = 3.13.18
executable = /usr/local/bin/python3.13
command = /usr/local/bin/python3 -m venv /home/user/env-project/venv

각 폴더와 파일의 역할은 다음과 같습니다. (윈도우에서는 bin 대신 Scripts, lib 대신 Lib라는 이름입니다. 리눅스에서 보이는 lib64는 lib를 가리키는 바로 가기라서 신경 쓰지 않아도 됩니다.)

  • bin: 이 가상 환경의 실행 파일을 모아 둔 폴더입니다. python, pip, 그리고 활성화 스크립트 activate가 여기 있습니다.
  • lib: 이 가상 환경에 pip으로 설치한 라이브러리가 들어가는 폴더입니다. 정확히는 lib/python3.13/site-packages 안에 들어갑니다. 공용 site-packages 대신 쓰는, 이 프로젝트만의 site-packages입니다.
  • include: C 언어로 만든 부분이 있는 라이브러리를 설치할 때 쓰는 헤더 파일을 위한 폴더입니다. 넘파이처럼 성능을 위해 C로 쓴 부분이 있는 라이브러리들이 있기 때문인데, 비어 있는 경우가 많으니 신경 쓰지 않아도 됩니다.
  • pyvenv.cfg: 가상 환경의 설정 파일입니다. home에는 이 가상 환경을 만든 원래 파이썬의 위치가 적혀 있습니다. 가상 환경을 써도 파이썬 자체와 표준 라이브러리는 이 원래 파이썬의 것을 그대로 쓰고, 그 밖의 라이브러리만 가상 환경의 lib에서 찾기 때문입니다.

그렇다면 활성화는 무엇을 하는 것일까요? 3.3에서 배쉬는 명령어를 입력받으면 PATH에 적힌 폴더들을 앞에서부터 차례로 뒤져서 그 이름의 실행 파일을 찾는다고 했습니다. 활성화 스크립트가 하는 핵심적인 일은, 가상 환경의 bin 폴더를 PATH의 맨 앞에 끼워 넣는 것입니다.

echo $PATH
source venv/bin/activate
echo $PATH
deactivate
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
/home/user/env-project/venv/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

그래서 활성화한 뒤에 python이나 pip이라고 입력하면, 배쉬는 가상 환경의 bin에서 먼저 그 실행 파일을 찾아 실행합니다. 그리고 이 python은 pyvenv.cfg를 보고 자기가 가상 환경 안에 있다는 것을 알아서, 라이브러리를 가상 환경의 lib에서 찾고, pip도 라이브러리를 거기에 설치합니다. deactivate는 PATH를 원래대로 되돌립니다. 정리하면, 가상 환경은 라이브러리를 찾고 설치하는 기준점을 컴퓨터 전체의 공용 폴더에서 프로젝트의 venv 폴더로 옮겨 놓는 것뿐입니다.

한 가지 기억해 둘 점은, 가상 환경이 원래 파이썬에 묶여 있다는 것입니다. 컴퓨터의 파이썬을 업데이트하거나 지우면 가상 환경이 동작하지 않을 수 있고, 그때는 가상 환경을 새로 만들고 requirements.txt로 라이브러리를 다시 설치해야 합니다. 또 requirements.txt는 라이브러리의 버전은 고정하지만, 파이썬 자체의 버전이나 운영체제까지 고정하지는 못합니다. 이 문제를 해결하는 것이 다음에 볼 컨테이너입니다.

가상 머신과 컨테이너

가상 환경은 라이브러리의 충돌을 막아 주는 것만으로도 꽤 유용하지만, 여전히 운영체제와 파이썬 버전에 묶여 있습니다. 파이썬 버전이 다르면 가상 환경도 달라지고, 운영체제가 다르면 실행 파일의 형식이나 경로가 달라지니, 가상 환경만으로는 다른 환경에서 코드를 완전히 재현하기 어렵습니다.

가상 머신

이 문제를 해결하는 가장 단순한 방법은 가상 머신입니다. 위에서 말한 앱플레이어가 바로 가상 머신입니다. 컴퓨터의 하드웨어 위에 원래 운영체제가 있는 상태에서, 가상화 계층을 하나 두고 그 위에 가상의 하드웨어를 만든 다음, 그 위에 완전히 별개의 운영체제를 설치해서 돌립니다. 원래 컴퓨터의 운영체제를 호스트 OS(host OS), 가상 머신 안의 운영체제를 게스트 OS(guest OS)라고 합니다. 호스트 OS가 윈도우라도, 게스트 OS로 리눅스를 띄우면 리눅스용으로 만든 프로젝트를 리눅스 환경에서 그대로 재현할 수 있습니다. 컴퓨터 안에 컴퓨터를 하나 더 가지게 되는 셈입니다. 하드웨어 수준부터 가상으로 만들기 때문에 하드웨어 수준의 가상화(hardware-level virtualization)라고도 합니다.

하지만 가상 머신은 개인이 프로젝트 하나를 재현하는 데 쓰기에는 좋은 방법이 아닙니다. 무엇보다 무겁습니다. 이미 운영체제 하나를 돌리고 있는데 그 위에 운영체제를 하나 더, 그것도 바탕화면과 그래픽 화면까지 통째로 돌리니 컴퓨터의 자원이 많이 듭니다. 컴퓨터가 아무리 좋아도 앱플레이어가 느렸던 경험이 있으실 텐데, 같은 이야기입니다. 이렇게 본래 작업 외에 추가로 드는 비용을 오버헤드(overhead)라고 합니다.

물론 가상 머신은 서버나 클라우드 같은 데이터 인프라에서는 거의 표준입니다. 관점이 다르기 때문입니다. 개인 개발자에게는 오버헤드가 부담이지만, 서버를 운영하는 쪽에서는 오버헤드를 감수하고서라도 확실한 격리와 안정적인 운영을 얻는 것이 더 중요합니다. 이것은 6장(데이터 사이언스의 인프라)에서 다시 다루겠습니다. 어쨌든 우리 입장에서는 가상 머신이 정답은 아니고, 대신 컨테이너를 씁니다.

컨테이너

컨테이너화(containerization)의 목적은 가상 머신과 같습니다. 호스트의 운영체제와 다른 운영체제 환경에서 코드를 재현할 수 있게 하는 것입니다. 차이는 그 목적을 이루는 방법에 있습니다. 컨테이너를 만드는 도구 가운데 가장 유명한 것은 도커(Docker)입니다. 너무 유명해서, 이미지 편집을 무엇으로 하든 “포토샵한다”고 말하듯이 컨테이너를 그냥 “도커”라고 부르는 경우가 많습니다.

가상 머신이 가상의 하드웨어를 만들고 그 위에 운영체제를 통째로 설치한다면, 컨테이너는 운영체제를 새로 띄우지 않습니다. 대신 호스트 운영체제의 리눅스 커널을 그대로 빌려 쓰면서, 프로그램이 실행되는 프로세스만 따로 격리된 공간에 가둡니다. 그 격리된 공간 안에는 우분투나 데비안 같은 리눅스 배포판의 파일들(기본 명령어와 라이브러리)과, 우리의 라이브러리와 코드만 들어 있습니다. 바탕화면도, 그래픽 화면도, 가상 하드웨어도 없습니다. 그래서 가상 머신에 비해 필요한 자원이 아주 적고, 켜고 끄는 것도 몇 초면 됩니다. 커널을 공유하면서 운영체제 수준에서 격리하기 때문에 운영체제 수준의 가상화(OS-level virtualization)라고도 합니다.

가상 머신 컨테이너
가상으로 만드는 것 하드웨어 전체 프로세스가 보는 환경
운영체제 게스트 OS를 통째로 설치 호스트의 커널을 빌려 씀
크기와 시작 시간 수 GB, 수십 초 이상 수십 MB~수 GB, 수 초
격리 수준 매우 강함 강하지만 커널을 공유함

리눅스 배포판들은 서로 달라도 커널은 같은 리눅스 커널이라는 것을 떠올리면, 컨테이너가 하는 일이 이해됩니다. 커널은 호스트의 것을 쓰고, 배포판의 차이나 라이브러리 버전의 차이로 결과가 달라지는 일은 컨테이너 안에 정해 둔 배포판과 라이브러리로 원천 차단하는 것입니다.

그렇다면 리눅스 커널이 없는 윈도우나 맥에서는 어떻게 할까요? 이때는 가상 머신과 비슷하게, 리눅스 커널을 돌리기 위한 아주 가벼운 가상 머신을 하나 몰래 띄워 두고 그 위에서 컨테이너들을 돌립니다. 윈도우에서는 3.1에서 본 WSL이 이 역할을 합니다. 그래서 호스트 OS가 리눅스라면 오버헤드가 거의 없고, 윈도우나 맥이라면 자원을 조금 더 쓰지만, 요즘에는 그 차이가 거의 무시해도 될 정도입니다.

도커

도커의 구조: 이미지와 컨테이너

도커는 두 프로그램이 주고받으며 동작합니다. 하나는 백그라운드에서 항상 돌면서 실제로 컨테이너를 만들고 관리하는 데몬(daemon, dockerd)이고, 다른 하나는 우리가 터미널에 입력하는 명령어를 데몬에게 전달하는 클라이언트(docker)입니다.

도커에서 가장 중요한 개념은 이미지(image)와 컨테이너(container)입니다.

  • 이미지는 컨테이너를 만들기 위한 틀입니다. 가벼운 리눅스 배포판, 필요한 라이브러리들, 그리고 우리의 코드가 층(layer)처럼 겹겹이 쌓여 있는 읽기 전용 묶음입니다. 한 번 만들어진 이미지는 바뀌지 않기 때문에, 같은 이미지에서는 언제나 같은 환경이 나옵니다.
  • 컨테이너는 이미지로부터 만들어 실제로 실행 중인(또는 실행했던) 인스턴스입니다. 객체 지향 프로그래밍의 클래스와 인스턴스의 관계와 같아서, 이미지 하나로 컨테이너를 여러 개 만들 수 있습니다.

이미지는 레지스트리(registry)라는 곳에 올려서 공유할 수 있습니다. 깃허브에서 코드를 공유하듯이, 도커 허브(Docker Hub)나 Quay.io 같은 레지스트리에서 이미지를 공유합니다. 다른 사람이 만든 이미지를 받아 쓰거나 내 이미지를 공유할 수 있으니, 재현 가능성을 높이기에 아주 좋습니다.

이렇게 보면 완벽한 도구 같지만, 주의할 점이 있습니다. 바로 보안입니다. 도커 데몬은 기본적으로 관리자 권한(root)으로 돌아가고, 도커 명령어를 쓸 수 있다는 것은 사실상 그 컴퓨터의 관리자 권한을 가진 것과 비슷합니다. 그래서 누군가 컨테이너를 뚫거나, 인터넷에 열려 있는 도커 데몬을 찾아내면 호스트 시스템 전체가 위험해질 수 있습니다. 실제로 보안 설정이 허술한 도커 서버들을 찾아다니며 퍼져서 암호화폐를 채굴하는 악성 프로그램이 발견된 적도 있습니다.1 그래서 신뢰할 수 있는 이미지만 쓰고, 도커 데몬을 인터넷에 열어 두지 않는 것이 기본입니다. 대학이나 연구소의 슈퍼컴퓨터처럼 많은 사람이 함께 쓰는 고성능 컴퓨팅(HPC) 환경에서는 이런 이유로 도커 대신 관리자 권한 없이 컨테이너를 돌리는 Apptainer(예전 이름은 Singularity) 같은 도구를 많이 씁니다.

도커 설치하기

  • Windows
  • macOS
  • Linux
  • Android (Termux)

윈도우에서는 Docker Desktop을 설치합니다. 먼저 내 컴퓨터의 CPU 종류를 확인합니다. 명령 프롬프트(cmd)에서 다음을 입력하면 AMD64나 ARM64가 나옵니다.

echo %PROCESSOR_ARCHITECTURE%

Docker Desktop 다운로드 페이지에서 이에 맞는 윈도우용 설치 파일을 받아 실행하면, 설치 프로그램이 알아서 필요한 것들을 설치합니다. 설치가 끝나면 컴퓨터를 다시 시작합니다. Docker Desktop을 처음 실행할 때 WSL을 설치하거나 업데이트하라는 창이 뜰 수 있는데, 위에서 말한 리눅스 커널을 돌리기 위한 가상 계층이니 안내대로 설치하면 됩니다. 이후 깃 배쉬나 파워셸에서 docker 명령어를 쓸 수 있습니다. 도커를 쓸 때는 Docker Desktop이 켜져 있어야 합니다.

Docker Desktop은 개인, 교육, 소규모 사업 용도로는 무료이지만, 일정 규모 이상의 회사에서 쓰려면 유료 구독이 필요합니다.

맥에서도 Docker Desktop을 설치합니다. 화면 왼쪽 위의 애플 메뉴에서 “이 Mac에 관하여”를 눌러, 칩이 Apple(M1, M2 등)인지 Intel인지 확인합니다. Docker Desktop 다운로드 페이지에서 이에 맞는 맥용 설치 파일(.dmg)을 받아, 응용 프로그램 폴더로 끌어다 놓아 설치합니다. 처음 실행할 때 권한을 요청하면 허용합니다. 이후 터미널에서 docker 명령어를 쓸 수 있고, 도커를 쓸 때는 Docker Desktop이 켜져 있어야 합니다.

Docker Desktop은 개인, 교육, 소규모 사업 용도로는 무료이지만, 일정 규모 이상의 회사에서 쓰려면 유료 구독이 필요합니다.

리눅스에서는 그래픽 화면이 있는 Docker Desktop 대신, 도커의 본체인 Docker Engine을 바로 설치하는 경우가 많습니다. 도커 공식 문서는 배포판별로 도커의 저장소를 등록해서 설치하는 방법을 안내하는데,2 연습용 컴퓨터라면 도커가 제공하는 설치 스크립트로 간단히 설치할 수도 있습니다.

curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh

설치하면 도커 명령어 앞에 매번 sudo를 붙여야 하는데, 내 계정을 docker 그룹에 넣으면 sudo 없이 쓸 수 있습니다. 다만 위의 보안 이야기처럼 이것은 그 계정에 사실상 관리자 권한을 주는 것이니, 개인 컴퓨터에서만 하세요. 설정 후에는 로그아웃했다가 다시 로그인해야 적용됩니다.

sudo usermod -aG docker $USER

아쉽게도 Termux에서는 도커를 쓸 수 없습니다. 컨테이너를 만드는 데 필요한 커널 기능을 안드로이드가 일반 앱에 허용하지 않기 때문입니다. 안드로이드 기기에서 도커 환경이 필요하다면, 컴퓨터나 클라우드 서버에 도커를 설치하고 거기에 접속해서 쓰는 방법이 현실적입니다. 아래의 내용은 원리를 이해하는 정도로 읽어 주세요.

첫 컨테이너 실행하기

설치가 끝났다면 터미널에서 다음을 입력해 봅니다. (이 글을 쓴 환경에는 도커가 설치되어 있지 않아서, 이 절의 명령어들은 실행 결과 없이 명령어만 적었습니다.)

docker run hello-world

docker run hello-world는 hello-world라는 이미지로 컨테이너를 만들어 실행하라는 명령어입니다. 처음 실행하면 다음과 같은 일이 차례로 일어나고, 출력에도 이 과정이 친절하게 적혀 나옵니다.

  1. 도커가 먼저 내 컴퓨터에서 hello-world 이미지를 찾습니다. 아직 받은 이미지가 없으니 Unable to find image 'hello-world:latest' locally라는 메시지가 나옵니다.
  2. 그래서 레지스트리인 도커 허브에서 이미지를 찾아 내려받습니다. hello-world는 연습용으로 도커 허브에 올라와 있는 이미지입니다.
  3. 받은 이미지로 새 컨테이너를 만들고 실행합니다. 이 컨테이너가 하는 일은 Hello from Docker!로 시작하는 안내문을 출력하는 것뿐입니다.
  4. 출력이 끝나면 컨테이너는 종료됩니다.

다른 이미지도 마찬가지입니다. hello-world가 안내문을 출력하는 프로그램을 실행했듯이, 컨테이너는 이미지에 정해 둔 프로그램을 실행합니다. 우리는 이 “정해 둔 프로그램”으로 파이썬 분석 코드나 주피터 같은 것을 쓰게 됩니다. docker run은 실행할 때마다 이미지로부터 새 컨테이너를 만들고, 대부분의 컨테이너는 프로그램을 한 번 실행하고 종료된 상태로 남습니다. (웹 서비스처럼 계속 돌아야 하는 프로그램이라면 종료되지 않고 계속 실행됩니다.) 지금까지 만든 컨테이너는 다음 명령어로 볼 수 있습니다.

docker ps -a

컨테이너마다 ID, 만든 이미지, 만든 시각, 상태 등이 나오는데, 위의 컨테이너는 상태가 Exited로 나옵니다. 더 이상 필요 없는 컨테이너는 ID를 써서 지울 수 있습니다.

docker rm <컨테이너 ID>

주피터 컨테이너 띄우기

데이터 사이언스에서 도커를 쓰는 대표적인 예는 주피터입니다. 주피터 개발팀은 데이터 분석에 필요한 라이브러리를 미리 설치해 둔 이미지들(Jupyter Docker Stacks)을 공개하고 있어서, 대부분의 경우 새 이미지를 만들 필요 없이 이것을 가져다 쓰면 됩니다.3 예를 들어 scipy-notebook에는 넘파이, 판다스, 맷플롯립 같은 과학 계산 라이브러리가 들어 있고, datascience-notebook에는 여기에 R과 줄리아까지 들어 있습니다. 이 이미지들은 Quay.io라는 레지스트리에 올라와 있습니다. 프로젝트 폴더로 이동한 다음 다음과 같이 실행합니다.

  • Windows
  • macOS
  • Linux
  • Android (Termux)

깃 배쉬에서는 다음과 같이 입력합니다.

docker run -it --rm -p 10000:8888 -v "//$(pwd)":/home/jovyan/work quay.io/jupyter/scipy-notebook:2026-07-28

$(pwd) 앞에 /를 하나 더 붙인 이유는, 깃 배쉬가 /로 시작하는 경로를 윈도우 경로로 멋대로 바꿔 버리는 것을 막기 위해서입니다. 파워셸에서는 다음과 같이 씁니다.

docker run -it --rm -p 10000:8888 -v "${PWD}:/home/jovyan/work" quay.io/jupyter/scipy-notebook:2026-07-28
docker run -it --rm -p 10000:8888 -v "$(pwd)":/home/jovyan/work quay.io/jupyter/scipy-notebook:2026-07-28
docker run -it --rm -p 10000:8888 -v "$(pwd)":/home/jovyan/work quay.io/jupyter/scipy-notebook:2026-07-28

Termux에서는 도커를 쓸 수 없습니다. 위의 Linux 탭을 참고해 주세요.

명령어가 길지만 하나씩 보면 어렵지 않습니다.

  • -it: 컨테이너의 출력을 지금 터미널에 보여 주고, 키보드 입력도 넘겨 줍니다.
  • --rm: 컨테이너가 종료되면 자동으로 지웁니다. docker ps -a에 종료된 컨테이너가 쌓이지 않습니다.
  • -p 10000:8888: 포트 연결입니다. 컨테이너 안의 주피터는 8888번 포트에서 접속을 기다리는데, 컨테이너는 격리되어 있어서 바깥에서 바로 들어갈 수 없습니다. 그래서 내 컴퓨터(호스트)의 10000번 포트로 들어오는 접속을 컨테이너의 8888번 포트로 넘겨 주라고 연결해 둡니다. 순서는 호스트:컨테이너입니다.
  • -v "$(pwd)":/home/jovyan/work: 볼륨 연결입니다. 지금 폴더($(pwd), 3.3의 명령어 치환)를 컨테이너 안의 /home/jovyan/work 폴더로 연결합니다. 주피터에서 work 폴더에 저장한 파일은 실제로는 내 컴퓨터의 프로젝트 폴더에 저장됩니다. jovyan은 이 이미지 안의 사용자 이름입니다.
  • quay.io/jupyter/scipy-notebook:2026-07-28: 사용할 이미지입니다. 레지스트리/이름:태그 모양인데, 태그(tag)는 이미지의 버전입니다.

태그를 적지 않으면 latest라는 태그를 쓰는데, latest는 이름 그대로 그때그때의 최신 버전을 가리키기 때문에 시간이 지나면 다른 이미지가 됩니다. 3.8에서 본 깃의 브랜치처럼 움직이는 이름표인 셈입니다. 재현 가능성을 지키려면 위처럼 날짜가 적힌 태그를 고정해 두는 것이 좋습니다. 그래야 몇 달 뒤에도 똑같은 이미지로 똑같은 환경을 만들 수 있습니다. 쓸 수 있는 태그는 Quay.io의 이미지 페이지에서 확인할 수 있습니다.

처음 실행하면 이미지를 이루는 층들을 하나씩 내려받느라 시간이 좀 걸립니다. 한 번 받은 이미지는 다음부터 다시 받지 않습니다. 다 받고 나면 주피터가 실행되면서 많은 메시지가 나오는데, 맨 아래쪽에 http://127.0.0.1:8888/lab?token=... 같은 주소가 있습니다. 이 주소를 통째로 복사해 브라우저에 붙여 넣되, 8888을 10000으로 바꿔야 합니다. 주피터는 자기가 컨테이너 안의 8888번 포트에서 돌고 있다는 것만 알고, 바깥에서 우리가 10000번 포트로 연결해 두었다는 것은 모르기 때문입니다. 주소를 고쳐서 들어가면 익숙한 주피터 화면이 나옵니다.

이 주피터에서 실행하는 코드는 모두 컨테이너 안, 즉 이미지에 정해 둔 리눅스 배포판과 라이브러리 위에서 실행됩니다. 컨테이너를 끝내려면 도커 명령어를 입력했던 터미널로 돌아가서 Ctrl + C를 누릅니다. 그러면 컨테이너가 종료되고, 브라우저의 주피터 화면은 남아 있지만 컨테이너와의 연결이 끊겨서 더 이상 코드를 실행할 수 없습니다. 그래도 work 폴더에 저장한 노트북과 데이터는 내 컴퓨터의 프로젝트 폴더에 그대로 남아 있습니다. 컨테이너는 실행만 대신해 줄 뿐이니까요.

Docker Compose로 간단하게

그런데 주피터를 켤 때마다 저 긴 명령어를 입력하는 것은 번거롭습니다. 그래서 컨테이너를 어떻게 실행할지를 파일에 적어 두고 짧은 명령어로 실행하게 해 주는 Docker Compose라는 기능이 있습니다. 프로젝트 폴더에 compose.yaml이라는 파일을 만들고 다음 내용을 적습니다.

compose.yaml
services:
  notebook:
    image: quay.io/jupyter/scipy-notebook:2026-07-28
    volumes:
      - .:/home/jovyan/work
    ports:
      - "10000:8888"
    container_name: my_notebook

위의 docker run 명령어에 적었던 이미지, 볼륨, 포트를 그대로 옮겨 적은 것입니다. YAML이라는 형식의 파일인데, 들여쓰기로 구조를 나타내니 공백 칸 수를 정확히 맞춰야 합니다. (예전 자료에서는 파일 이름을 docker-compose.yml로 하고, 맨 위에 version: "3" 같은 줄을 적는 경우가 많은데, 지금은 version 줄이 필요 없습니다.) 이 파일을 저장한 다음, 터미널이 프로젝트 폴더를 바라보게 하고 다음을 입력하면 파일에 적힌 대로 주피터가 실행됩니다.

docker compose up

끄려면 Ctrl + C를 누르거나, 다른 터미널에서 docker compose down을 입력합니다. 예전에는 docker-compose라는 별도의 프로그램으로 docker-compose up이라고 입력했는데, 지금은 도커에 기능이 합쳐져서 docker compose(공백)로 씁니다. 이 compose.yaml도 requirements.txt처럼 깃으로 커밋해 두면, 저장소를 받은 사람은 docker compose up 한 줄로 나와 똑같은 환경을 얻을 수 있습니다.

여기서는 도커의 아주 기본적인 이야기만 다뤘습니다. 이 글의 목적은 도커를 제대로 쓰는 법을 익히는 것이 아니라, 재현 가능성을 위해 어떤 방법들이 있는지를 소개하는 것이기 때문입니다. 직접 이미지를 만드는 Dockerfile 같은 내용은 도커 공식 문서의 튜토리얼을 따라 해 보시기를 권합니다.

정리

  • 코드의 결과는 코드만이 아니라 하드웨어, 커널, 운영체제, 라이브러리로 이루어진 환경 전체가 만들어 냅니다. 재현 가능성을 가장 자주 깨는 것은 라이브러리입니다.
  • 가상 환경(venv)은 라이브러리를 프로젝트마다 따로 설치해서 충돌을 막습니다. python3 -m venv venv로 만들고, 운영체제에 맞는 명령어로 활성화하고, deactivate로 끕니다.
  • pip freeze > requirements.txt로 라이브러리 목록을 저장하고, pip install -r requirements.txt로 같은 환경을 만듭니다. 가상 환경 폴더는 공유하지 않습니다.
  • 가상 환경은 활성화할 때 PATH의 맨 앞에 자기 bin 폴더를 넣어서, 라이브러리를 찾고 설치하는 기준점을 프로젝트 폴더로 옮깁니다.
  • 가상 머신은 하드웨어부터 가상으로 만들어 운영체제를 통째로 돌리고, 컨테이너는 호스트의 커널을 빌려 쓰면서 프로세스만 격리합니다. 컨테이너가 훨씬 가볍습니다.
  • 도커에서 이미지는 틀, 컨테이너는 그 틀로 만든 인스턴스입니다. 이미지의 태그를 고정하고, compose.yaml을 공유하면 누구나 같은 환경을 얻을 수 있습니다.

이렇게 환경까지 고정했다면 재현 가능성을 위한 준비는 거의 끝났습니다. 마지막으로, 그 환경 위에서 코드가 정말 의도대로 동작하는지를 자동으로 확인하는 방법을 다음 글에서 살펴보겠습니다.
