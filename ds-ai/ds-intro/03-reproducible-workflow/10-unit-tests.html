3.10 단위 테스트

3장 재현 가능한 작업 환경 · 코드가 의도대로 동작하는지 자동으로 확인하기

데이터 사이언스·AI
데이터 사이언스 개론
코드를 모듈로 나누고, pytest로 함수마다 단위 테스트를 작성해 실행하는 법을 실제 실행 결과와 함께 살펴봅니다. assert, 실패한 테스트 읽기, 테스트 클래스, parametrize, 정답을 아는 토이 데이터와 예외 테스트, 여러 시드로 반복하는 테스트까지 다루고, 단위 테스트가 재현 가능성과 어떻게 이어지는지 정리합니다.
Published

November 4, 2026

들어가며

지난 글에서는 가상 환경과 컨테이너로 코드가 실행되는 환경을 고정하는 법을 살펴보았습니다. 이 정도면 환경을 일관되게 유지하기 위해 할 수 있는 일은 거의 다 했다고 볼 수 있습니다. 이번 글에서는 여기에 한 가지를 더해서, 그 환경 위에서 코드가 정말 의도대로 동작하는지를 자동으로 확인하는 단위 테스트(unit test)를 다룹니다. 단위 테스트는 재현 가능성만을 위한 도구가 아니라 소프트웨어 개발 전반에서 쓰이는 도구인데, 여기서는 그 개념을 짧게 소개하고 재현 가능성과 어떻게 이어지는지를 살펴보겠습니다.

코딩은 테스트의 반복입니다

우리는 보통 다음 과정을 반복하며 코드를 짭니다.

  1. 결과를 예상하고 코드를 씁니다.
  2. 코드를 실행해서 결과를 봅니다.
  3. 예상과 결과를 비교하고, 다르면 고칩니다.

큰 프로그램을 짜는 것도 결국 이 세 단계를 겹겹이 반복하는 것입니다. 그래서 코딩은 이 세 개의 톱니바퀴가 계속 맞물려 돌아가는 과정이라고 할 수 있고, 이 톱니바퀴는 결국 코드를 시험해 보는 과정이니, 코딩 자체가 테스트의 반복이라고도 할 수 있습니다.

이렇게 단계를 나눠 생각해 보지 않았을 뿐, 지금까지 우리도 이런 식으로 코딩을 해 왔습니다. 그리고 그 테스트를 매번 손으로 했을 것입니다. 함수를 짜고 몇 가지 값을 넣어서 출력을 눈으로 확인하는 식으로요. 간단한 프로그램이라면 이것도 나쁘지 않지만, 데이터 사이언스에서 다루는 복잡한 코드에서는 쉽지 않습니다. 함수가 수십 개이고, 하나를 고칠 때마다 다른 함수들이 여전히 잘 동작하는지 모두 손으로 확인해야 한다면 금방 지치게 됩니다. 이 테스트를 자동으로 해 주는 것이 단위 테스트입니다.

모듈로 나눠야 테스트할 수 있습니다

단위 테스트를 하려면 먼저 코드가 모듈(module)로 잘 나뉘어 있어야 합니다. 모듈화는 소스 코드 파일 하나에 모든 것을 다 구현하는 대신, 기계의 부품을 하나하나 만들어 조립하듯이 필요한 기능들을 여러 파일에 나눠 구현한 다음 하나로 모으는 것입니다. 이렇게 해야 테스트도 쉽습니다. 파일마다, 함수마다 따로 테스트하고, 문제가 있는 부분만 고치면 되니까요.

자동차를 생각하면 쉽습니다. 차체와 바퀴가 별개의 부품이 아니라 하나로 붙어 있다면, 바퀴에 문제가 생겨도 차체와 바퀴를 통째로 수리해야 합니다. 하지만 따로 떨어진 부품이라면 문제가 있는 바퀴만 고치면 됩니다. 3.5에서 재사용성을 이야기하며 코드를 잘 쪼개라고 한 것도 같은 이유입니다.

주피터 노트북으로 데이터 사이언스 프로젝트를 할 때는 보통, 실제로 분석을 실행하고 그림을 그리는 노트북 파일(.ipynb)과, 분석에 필요한 기능(함수)들을 모아 둔 파이썬 소스 코드 파일(.py)로 나눕니다. 노트북에서는 .py 파일의 함수를 불러와 쓰고, 단위 테스트는 .py 파일의 함수들을 대상으로 합니다.

pytest로 첫 테스트 쓰기

파이썬에서 단위 테스트에 가장 많이 쓰는 도구는 pytest입니다.1 지난 글의 가상 환경을 활성화한 상태에서 pip으로 설치합니다.

pip install pytest numpy

예를 들어 functions.py라는 파일에 평균을 계산하는 함수가 있다고 해 보겠습니다.

functions.py
import numpy as np


def average(data: np.ndarray) -> float:
    """넘파이 배열의 산술 평균을 계산합니다."""
    return data.sum() / len(data)

이 함수를 테스트하려면 test_functions.py라는 파일을 새로 만들고, 테스트할 함수를 불러온 다음 테스트 함수를 씁니다.

test_functions.py
import numpy as np

from functions import average


def test_average():
    rng = np.random.default_rng(1557)
    test_data = rng.standard_normal(10)
    assert abs(test_data.mean() - average(test_data)) < 1e-8

test_average()는 시드를 1557로 고정한 난수 10개를 만들어서, 넘파이의 mean() 메서드가 계산한 평균과 우리가 만든 average()가 계산한 평균의 차이가 충분히 작은지를 확인합니다. 넘파이의 mean()은 이미 많은 사람이 검증한 함수이니, 이것과 결과가 같다면 우리 함수도 맞게 계산했다고 볼 수 있습니다.

마지막 줄에서 보통 함수가 값을 돌려줄 때 쓰는 return 대신 assert를 쓴 것이 보입니다. assert는 값을 돌려주려는 것이 아니라, 개발하면서 코드의 논리적인 오류를 찾으려고 쓰는 문장입니다. assert 뒤의 조건이 참이면 아무 일도 일어나지 않고 넘어가고, 거짓이면 AssertionError라는 예외를 냅니다. 그래서 assert는 “이 조건은 반드시 참이어야 한다”는 약속을 코드로 적어 두는 것이라고 할 수 있습니다.

두 평균이 정확히 같은지(==)가 아니라 차이가 \(10^{-8}\)보다 작은지를 확인하는 이유는, 컴퓨터의 실수 계산에는 아주 작은 반올림 오차가 있기 때문입니다. 수학적으로 같은 계산이라도 더하는 순서가 다르면 마지막 자리가 조금 달라질 수 있습니다. 그래서 실수를 비교하는 테스트에서는 이렇게 허용 오차를 둡니다. (pytest의 pytest.approx나 넘파이의 np.isclose를 써도 됩니다.)

참고로 from functions import average 대신 from functions import average, np라고 써서, functions.py가 불러온 넘파이를 그대로 가져올 수도 있습니다. 이렇게 해도 동작하지만, 3.6의 The Zen of Python이 말하듯 “명시적인 것이 암시적인 것보다 낫기” 때문에, 테스트 파일에서도 필요한 것은 직접 import numpy as np로 불러오는 편이 읽기 좋습니다.

이제 테스트를 실행합니다. 터미널이 프로젝트 폴더를 바라보게 한 다음 pytest라고만 입력하면 됩니다.

ls
pytest

테스트가 실패하면

테스트의 진가는 실패할 때 드러납니다. 누군가 2.2의 표본 분산과 헷갈려서, average()를 \(n\)이 아니라 \(n-1\)로 나누도록 고쳐 버렸다고 해 보겠습니다.

functions.py
import numpy as np


def average(data: np.ndarray) -> float:
    """넘파이 배열의 산술 평균을 계산합니다."""
    return data.sum() / (len(data) - 1)

테스트 여러 개와 테스트 클래스

average()를 여러 방식으로 검사하고 싶다면 테스트 함수를 여러 개 쓰면 되고, variance() 같은 다른 함수도 같은 방식으로 테스트 함수를 써서 test_functions.py에 함께 넣으면 됩니다. 테스트가 많아지면 관련 있는 테스트들을 클래스로 묶을 수도 있습니다. 클래스의 이름은 Test로 시작해야 pytest가 찾아냅니다.

    """평균과 분산 함수에 대한 테스트를 묶어 둔 클래스입니다."""

여러 입력으로 한 번에: parametrize

지금까지의 테스트 함수는 각각 한 번씩 실행되었습니다. 같은 테스트를 여러 입력값으로 반복하고 싶다면, 입력마다 테스트 함수를 따로 쓰는 대신 pytest의 parametrize를 쓸 수 있습니다.

test_parametrize.py
import numpy as np
import pytest

from functions import average

rng = np.random.default_rng(1557)
test_data = rng.standard_normal(100)


@pytest.mark.parametrize(
    "n, expected", [(n, test_data[:n].mean()) for n in range(10, 101, 10)]
)
def test_average(n, expected):
    assert abs(expected - average(test_data[:n])) < 1e-8

@pytest.mark.parametrize는 함수 바로 위에 붙이는 데코레이터(decorator)로, 아래의 테스트 함수를 여러 입력값으로 반복 실행하라는 뜻입니다. 첫 번째 인자 "n, expected"는 테스트 함수에 넘길 인자의 이름이고, 두 번째 인자는 그 값들의 목록입니다. 목록은 리스트를 한 줄로 만드는 파이썬 문법인 리스트 컴프리헨션(list comprehension)으로 만들었는데, n이 10, 20, …, 100일 때마다 (n, 앞의 n개의 평균)이라는 짝을 만듭니다. 그러면 pytest는 앞의 10개로 한 번, 20개로 한 번, … 100개 전체로 한 번, 모두 10번의 테스트를 실행합니다.

정답을 아는 데이터로 테스트하기

지금까지는 넘파이의 결과와 비교했는데, 3.5에서 이야기한 토이 데이터처럼 정답을 손으로 계산할 수 있는 작은 데이터로 테스트하는 것도 좋은 방법입니다. 그리고 3.5의 견고함에서 본 것처럼 이상한 입력에 분명한 오류를 내도록 만들었다면, 정말 그 오류가 나는지도 테스트할 수 있습니다. 빈 배열이 들어오면 ValueError를 내도록 average()를 고치고, 테스트를 추가해 보겠습니다.

functions.py
import numpy as np


def average(data: np.ndarray) -> float:
    """넘파이 배열의 산술 평균을 계산합니다. 빈 배열이면 ValueError를 냅니다."""
    if len(data) == 0:
        raise ValueError("data is empty")
    return data.sum() / len(data)


def variance(data: np.ndarray) -> float:
    """넘파이 배열의 표본 분산(n-1로 나눈 분산)을 계산합니다."""
    return ((data - average(data)) ** 2).sum() / (len(data) - 1)
test_known.py
import numpy as np
import pytest

from functions import average, variance


def test_average_known_values():
    assert average(np.array([1.0, 2.0, 3.0, 4.0])) == pytest.approx(2.5)


def test_variance_known_values():
    # 평균이 5이고, 편차의 제곱의 합이 32이므로 표본 분산은 32 / 7입니다.
    data = np.array([2.0, 4.0, 4.0, 4.0, 5.0, 5.0, 7.0, 9.0])
    assert variance(data) == pytest.approx(32 / 7)


def test_average_empty_raises():
    with pytest.raises(ValueError):
        average(np.array([]))

pytest.approx(2.5)는 앞에서 말한 허용 오차를 알아서 둔 채로 2.5와 같은지 비교해 줍니다. pytest.raises(ValueError)는 그 아래 블록에서 ValueError가 나야 테스트가 통과한다는 뜻입니다. 오류가 나지 않으면 오히려 테스트가 실패합니다. 이제 모든 테스트를 한 번에 실행해 보겠습니다.

단위 테스트와 재현 가능성

여기까지 읽으면 이런 의문이 들 수 있습니다. “테스트가 중요하고 편리한 건 알겠는데, 이게 재현 가능성이랑 무슨 상관이지?” 충분히 그렇게 느낄 수 있습니다. 실제로 pytest만 놓고 보면 그냥 테스트 도구입니다. 하지만 지난 글의 가상 환경이나 도커와 함께 쓰면, 재현 가능성을 확인하는 도구가 됩니다.

고정된 환경에서 테스트하기

지난 글에서 requirements.txt나 도커 이미지로 환경을 고정하고 공유하는 법을 보았습니다. 이렇게 고정한 환경에서 테스트를 돌리면, 내 컴퓨터가 아닌 다른 컴퓨터에서도 같은 환경에서는 같은 테스트 결과가 나오는지 확인할 수 있습니다. 저장소를 받은 사람이 가상 환경을 만들고 pip install -r requirements.txt를 한 다음 pytest를 돌려서 모두 통과한다면, 적어도 테스트가 확인하는 범위에서는 코드가 내 컴퓨터에서와 똑같이 동작한다는 뜻입니다. 반대로 라이브러리가 업데이트된 뒤 테스트가 실패한다면, 지난 글에서 말한 “기본값이 조용히 바뀌는” 종류의 문제를 결과를 보고하기 전에 잡아낼 수 있습니다.

실제로 많은 프로젝트는 깃허브에 코드를 푸시할 때마다, 새로 만든 깨끗한 환경에서 테스트를 자동으로 돌리도록 설정해 둡니다. 이것을 지속적 통합(continuous integration, CI)이라고 합니다. 깃허브에서는 GitHub Actions라는 기능으로 할 수 있는데, 이 사이트도 글을 푸시하면 GitHub Actions가 깨끗한 환경에서 사이트를 새로 만들어 배포하도록 되어 있습니다.

시드가 운 좋게 골라진 것은 아닐까요?

3.5에서 데이터 사이언스의 재현성을 가장 자주 깨는 것이 난수라고 했고, 그래서 시드를 고정한다고 했습니다. 그런데 시드를 고정하면 결과는 재현되지만, 새로운 걱정이 하나 생깁니다. 그 결과가 우연히 잘 뽑힌 시드 덕분은 아닐까 하는 것입니다. 시드 하나에서만 잘 동작하는 알고리즘이라면, 코드에 녹인 아이디어가 좋았던 것이 아니라 운이 좋았던 것일 수 있습니다.

parametrize로 여러 시드에 대해 같은 테스트를 반복하면 이것을 구분할 수 있습니다. 예를 들어 표준정규분포에서 뽑은 표본 1,000개의 표본 분산이, 참값 1에서 크게 벗어나지 않는지를 시드 세 개로 확인해 보겠습니다. 여기서는 이 사이트에서 쓰는 시드 1557, 88848, 2400을 씁니다.

test_seeds.py
import numpy as np
import pytest

from functions import variance


@pytest.mark.parametrize("seed", [1557, 88848, 2400])
def test_variance_close_to_true_value(seed):
    rng = np.random.default_rng(seed)
    sample = rng.standard_normal(1000)
    # 표준정규분포의 분산은 1입니다. 표본이 1,000개면 표본 분산은 대개 0.9와 1.1 사이에 있습니다.
    assert abs(variance(sample) - 1) < 0.1

정리

  • 코딩은 결과를 예상하고, 실행하고, 비교하는 테스트의 반복입니다. 단위 테스트는 이 테스트를 함수 단위로 자동화합니다.
  • 테스트하려면 코드가 모듈로 잘 나뉘어 있어야 합니다. 노트북에서는 분석을, .py 파일에서는 함수를 관리하고 테스트합니다.
  • pytest는 test_*.py 파일의 test로 시작하는 함수를 찾아 실행합니다. 테스트 함수 안에서는 assert로 반드시 참이어야 하는 조건을 적습니다.
  • 실수는 abs(a - b) < 허용오차나 pytest.approx로 비교하고, 테스트 클래스로 테스트를 묶고, parametrize로 여러 입력에 대해 반복하며, pytest.raises로 예외가 나는지 확인합니다.
  • 정답을 아는 토이 데이터로 테스트하고, 고정된 환경에서 테스트를 돌리고, 여러 시드로 반복하면, 결과가 재현되는지와 그 결과가 우연이 아닌지를 함께 확인할 수 있습니다.

이것으로 3장의 재현 가능성에 관한 이야기가 끝납니다. 셸로 데이터를 다루는 과정을 명령어로 남기고, 읽기 좋은 코드를 쓰고, 깃으로 버전을 관리하고, 가상 환경과 컨테이너로 환경을 고정하고, 단위 테스트로 동작을 확인하는 것까지, 이 정도면 데이터 사이언스의 방법론을 공부하기 전에 갖춰야 할 마음가짐과 도구는 모두 갖춘 셈입니다.

사실 제 생각에 3장이 데이터 사이언스 개론 전체에서 가장 어려운 장이 아닌가 합니다. 다른 장들은 아이디어를 휴리스틱 수준에서 이해하는 것에서 끝나는데, 이 장은 그걸 넘어서서 그래서 그걸 어떻게 하냐가 좀 구체적으로 다뤄지는 편이라서요. 쓰고보니까 뭔가 개론 레벨에서 더 직관적이고 쉬운 부분만을 다루는 게 나았나 싶지만, 그렇다고 또 이 3장의 내용을 다른 핵심 혹은 심화로 독립적으로 별개로 넘기기엔 또 내용이 너무 애매해서 걍 여기서 다 해결하고 넘어가자는 마인드였다보니, 그냥… 그렇게 됐습니다 ㅋㅋ

다음 장에서는 2장의 기술 통계에서 한 걸음 더 나아가, 데이터로부터 의미 있는 명제를 실제로 추론하는 이야기를 이어 가겠습니다. 여기서부터는 다시 좀 더 비교적 휴리스틱을 다루는 더 직관적인 이야기로 돌아가게 됩니다.
